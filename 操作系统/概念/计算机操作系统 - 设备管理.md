## 一、机械硬盘（HDD）

### 磁盘结构

- 盘面（Platter）：一个磁盘有多个盘面；
- 磁道（Track）：盘面上的圆形带状区域，一个盘面可以有多个磁道；
- 扇区（Sector）：磁道上的一个弧段，一个磁道可以有多个扇区，它是最小的物理储存单位，目前主要有 512 bytes 与 4 K 两种大小；
- 磁头（Head）：与盘面非常接近，能够将盘面上的磁场转换为电信号（读），或者将电信号转换为盘面的磁场（写）；
- 制动手臂（Actuator arm）：用于在磁道之间移动磁头；
- 主轴（Spindle）：使整个盘面转动。

### 访问时间构成

读写一个磁盘块的时间由三部分组成：

| 组成 | 说明 | 典型耗时 |
|:---|:---|:---|
| **寻道时间** | 制动手臂移动磁头到目标磁道 | **3~15 ms** |
| **旋转延迟** | 主轴转动使目标扇区转到磁头下 | 平均为旋转半圈时间，7200 RPM 约 **4 ms** |
| **传输时间** | 实际读写数据 | 微秒级 |

**关键结论**：**寻道时间最长，占据了主要开销**。因此 HDD 时代磁盘调度的核心目标是——**减少磁头移动，使平均寻道时间最短**。

> ⚠️ **这个前提在 SSD 上完全不成立**（SSD 无机械部件，没有寻道和旋转），这是理解现代设备管理的关键转折点。

## 二、磁盘调度算法（HDD 时代）

### 1. 先来先服务

> FCFS, First Come First Served

按照磁盘请求的**到达顺序**进行调度。

- **优点**：公平、简单，不会出现饥饿。
- **缺点**：未对寻道做任何优化，磁头可能来回大幅度移动，平均寻道时间长。

### 2. 最短寻道时间优先

> SSTF, Shortest Seek Time First

优先调度与**当前磁头所在磁道距离最近**的请求。

- **优点**：平均寻道时间较短。
- **缺点**：**不公平，会出现饥饿**。如果新到达的请求总是比等待中的请求更近，那么远处的请求会一直等待——**两端磁道的请求最容易饥饿**。

### 3. 电梯算法

> SCAN

电梯总是保持一个方向运行，直到该方向没有请求为止，然后改变运行方向。

电梯算法（扫描算法）和电梯运行过程类似：按一个方向进行磁盘调度，直到该方向上没有未完成的请求，才改变方向。

- **优点**：考虑了移动方向，**解决了 SSTF 的饥饿问题**，所有请求都会被满足。
- **改进**：C-SCAN（循环扫描）只单向扫描，返回时不服务请求，使各磁道等待时间更均匀。

### 4. 调度算法的现代适用性

**这些算法在今天还有用吗？**

| 场景 | 是否使用磁盘调度算法 |
|:---|:---|
| **HDD（机械硬盘）** | ✅ 仍在使用，SCAN 及其变种是主流 |
| **SSD（固态硬盘）** | ❌ **基本不用**，见下方说明 |
| **服务器存储阵列** | ⚠️ 由阵列控制器统一调度，OS 层调度被弱化 |

**为什么 SSD 不需要磁盘调度算法？**

- **没有寻道和旋转延迟**——访问任意位置的耗时几乎相同（随机读延迟约 50~100 μs）。
- 排序请求**无法带来收益**，反而增加调度开销。
- 现代内核（如 Linux）对 SSD 通常使用 **`none`（无调度）/ `mq-deadline`** 而非 `cfq`。

> **面试提示**：如果被问到「SSD 环境下磁盘调度算法还有意义吗」，核心回答是——**调度的前提（寻道开销）消失了，因此经典算法在 SSD 上收益很低；SSD 的性能优化重心转移到了 FTL、GC、TRIM、队列深度这些机制上**。

## 三、固态硬盘（SSD）

SSD 基于 **NAND Flash**（闪存），与 HDD 的物理原理完全不同。它的瓶颈不在「机械运动」，而在**闪存的物理特性**。

### 闪存的基本结构

```text
SSD
 ├── Die（晶粒）
 │    └── Plane
 │         └── Block（块）      ← 擦除的最小单位
 │              └── Page（页）  ← 读/写的最小单位
```

| 单位 | 大小 | 操作支持 |
|:---|:---|:---|
| **Page（页）** | 通常 4 KB ~ 16 KB | **读、写** |
| **Block（块）** | 通常 128 ~ 256 个 Page | **擦除**（整块） |

**闪存的三个关键限制**（这是理解 SSD 一切机制的根源）：

| 限制 | 说明 |
|:---|:---|
| **① 读写的粒度是「页」，擦除的粒度是「块」** | 想改一个页，必须擦除整个块 |
| **② 写之前必须先擦除** | 不能直接覆盖写，只能写入「干净」的页 |
| **③ 擦写次数有限** | 每个块的 P/E（Program/Erase）次数有上限 |

**P/E 次数与寿命**：

| 闪存类型 | 典型 P/E 次数 | 用途 |
|:---|:---|:---|
| SLC（单层） | 约 10 万次 | 企业级、高耐久 |
| MLC（双层） | 约 3 千 ~ 1 万次 | 早期消费级 |
| TLC（三层） | 约 1 千 ~ 3 千次 | **当前主流消费级** |
| QLC（四层） | 约 100 ~ 1 千次 | 大容量、低成本 |

> **容量越大，寿命越长**：因为写入会被分摊到更多块上。一块 1TB 的 TLC 盘，按 1000 次 P/E 计算，总写入量可达约 1000 TBW。

### FTL：闪存转换层

**问题**：操作系统认为存储是「块设备」，可以随机覆盖写（如 LBA 逻辑块地址）。但闪存**不能覆盖写，且擦除粒度是块**。这两者的矛盾怎么解决？

**答案：FTL（Flash Translation Layer，闪存转换层）**。

FTL 是 SSD 控制器中的固件，负责把**逻辑地址（LBA）**映射到**物理地址（PBA）**：

```text
操作系统读写 LBA 1000
        ↓
FTL 查映射表：LBA 1000 → 物理 Page 8-100
        ↓
实际读写物理位置
```

**FTL 带来的关键能力——「异地更新」**：

当要修改 LBA 1000 的数据时，FTL **不擦除原位置**，而是：

```text
① 找一个空闲的 Page，写入新数据
② 更新映射表：LBA 1000 → 新物理位置
③ 标记旧位置为「无效」（invalid）
```

**这样做的好处**：避免了「为了改 4KB 就擦除整个 256KB 块」的巨大开销。

**代价**：产生了**无效页（垃圾）**，需要后续的**垃圾回收**来清理。

> **映射表的粒度**也是设计权衡：
> - **页级映射**：最灵活，但映射表巨大（1TB 按 4KB 页需约 1GB 内存）
> - **块级映射**：映射表小，但性能差
> - **混合映射**：折中方案，实际产品常用

### 垃圾回收（GC）与写放大

**为什么会产生垃圾？**

由于「异地更新」，旧数据被标记为无效但**仍占用物理页**。随着写入增多，盘上无效页越来越多，可用的「干净页」越来越少。

**垃圾回收（GC）做什么？**

当空闲块不足时，SSD 需要：

```text
① 选一个有较多无效页的 Block
② 把其中仍然有效的页读出来
③ 擦除整个 Block
④ 把有效页重新写入（到其他位置）
```

**写放大（Write Amplification, WA）**：

GC 过程中的「搬移有效数据」会导致**实际写入闪存的量大于主机请求的写入量**：

```text
WA = 实际写入闪存的数据量 / 主机请求写入的数据量
```

**写放大的危害**：

- **降低性能**：用户写入 4KB，SSD 内部可能实际写了 8KB 甚至更多
- **缩短寿命**：P/E 次数被额外消耗

**为什么「随机写」比「顺序写」差那么多？**

| 写入模式 | 无效页产生速度 | GC 触发频率 | 写放大 |
|:---|:---|:---|:---|
| **顺序写** | 慢（整块整块写满） | 低 | 接近 1 |
| **随机写** | 快（到处产生无效页） | 高 | 可达数倍甚至十几倍 |

**这也是「SSD 不要做碎片整理」的原因**——碎片整理会产生大量随机写，加剧 GC 和写放大，纯粹是伤害。

**降低写放大的手段**：

| 手段 | 说明 |
|:---|:---|
| **TRIM** | 让 SSD 提前知道哪些数据已失效 |
| **OP（预留空间）** | 保留一部分容量不暴露给 OS，供 GC 使用 |
| **顺序写优先** | 应用层尽量顺序写（如日志追加） |
| **合理分区** | 避免长期接近满盘（空闲块越少，GC 越频繁） |

> **重要经验**：**SSD 长期保持过高的使用率（如 >90%）会显著掉速**，因为空闲块不足，GC 频繁触发且没有腾挪空间。

### TRIM 命令

**问题背景**：

当用户**删除文件**时，操作系统只删除文件系统的元数据（标记该区域可用），**并不会通知 SSD**。SSD 并不知道这些数据已失效，GC 时仍会把它们当作有效数据**搬移**——做无用功，加剧写放大。

**TRIM 的作用**：

操作系统在删除数据时，**主动通知 SSD**：「这些 LBA 的数据已经失效了，你可以回收。」

```text
无 TRIM：
  删除文件 → OS 只标记 → SSD 不知情 → GC 仍搬移这些「垃圾」 → 写放大高

有 TRIM：
  删除文件 → OS 发送 TRIM → SSD 标记为无效 → GC 直接跳过 → 写放大低
```

**TRIM 是延迟生效的**——它只是「告知」，实际回收由 SSD 在空闲时（如 idle GC）异步完成，不阻塞用户操作。

**相关命令与检查**：

```bash
# 查看磁盘是否支持 TRIM
hdparm -I /dev/sda | grep TRIM

# 手动执行 TRIM（fstrim）
sudo fstrim -v /

# 查看文件系统的 discard 挂载选项
mount | grep discard
```

**TRIM 的两种模式**：

| 模式 | 说明 | 特点 |
|:---|:---|:---|
| **在线 TRIM**（`discard` 挂载选项） | 删除时**立即**发送 TRIM | 实时，但对性能有一定影响 |
| **批量 TRIM**（`fstrim` 定时任务） | 定期**统一**执行 | 推荐方式，系统默认每周执行 |

> Linux 上主流发行版默认启用 `fstrim.timer` 每周执行一次，这比实时 `discard` 更高效。
>
> ⚠️ **注意**：TRIM 会导致「已删除数据无法恢复」，这是数据恢复工具的常见失效原因。

### 磨损均衡

**问题**：闪存块的 P/E 次数有限。如果反复写同一个块（如频繁更新同一个文件），这个块会**先损坏**，整盘寿命受限于最弱的块。

**磨损均衡（Wear Leveling）**：让写入**均匀分布**到所有块上。

| 类型 | 说明 |
|:---|:---|
| **动态磨损均衡** | 优先使用**擦写次数少**的块（新写入时分摊） |
| **静态磨损均衡** | 主动搬移**长期不动的冷数据**，腾出低磨损块给热数据 |

**静态磨损均衡更关键**：如果没有它，那些从不被修改的「冷数据」会一直占着低磨损的块，而热数据反复擦写少数块，导致寿命不均。

**这也解释了「SSD 上的数据为什么会自己移动」**——SSD 后台会主动搬移冷数据来均衡磨损，这是正常现象。

### SSD 的访问时间构成

对比 HDD，SSD 的延迟构成完全不同：

| 操作 | 典型延迟 |
|:---|:---|
| **顺序读** | 约 50~100 μs |
| **随机读** | 约 50~100 μs（**与顺序读几乎相同**） |
| **写（需先擦除时）** | 可达 1 ms 以上（最坏情况） |

**关键差异**：

- **HDD**：随机访问比顺序访问慢 **数百倍**（寻道开销）
- **SSD**：随机与顺序访问**延迟接近**，性能差异主要来自**带宽和 GC**

> **这带来了重要的架构影响**：在 HDD 时代，数据库和文件系统设计极力追求「顺序访问」（如 B+ 树、日志结构）。在 SSD 时代，**随机访问的代价大幅降低**，一些 HDD 时代的优化变得不再必要，甚至有的设计（如 LSM-Tree）反而因为「写放大」在 SSD 上有新的权衡。

## 四、HDD 与 SSD 对比

| 对比维度 | HDD（机械硬盘） | SSD（固态硬盘） |
|:---|:---|:---|
| **存储原理** | 磁性介质 + 机械读写 | NAND 闪存 + 电子读写 |
| **寻道/旋转** | 有（主要延迟来源） | **无** |
| **随机读延迟** | 约 5~15 ms | 约 50~100 μs |
| **顺序/随机差异** | **差异巨大**（数百倍） | 差异小 |
| **抗震动** | 差（机械部件） | **好**（无机械部件） |
| **功耗与噪音** | 高、有噪音 | 低、**静音** |
| **单位容量成本** | **低** | 高 |
| **写入寿命** | 几乎无限（机械磨损为主） | **有限**（P/E 次数） |
| **需要调度算法** | ✅ 需要 | ❌ 基本不需要 |
| **需要 TRIM** | ❌ | ✅ **必须** |
| **碎片整理** | ✅ 有益 | ❌ **有害** |
| **典型用途** | 冷数据、大容量存储、备份 | 系统盘、数据库、高并发场景 |

**选型建议**：

- **SSD**：操作系统、数据库、高频读写业务、需要低延迟的场景
- **HDD**：冷数据归档、大容量备份、成本敏感且对延迟不敏感的场景
- **混合**：SSD 做缓存/热数据 + HDD 做容量（如 ZFS 的 L2ARC、RAID 分层）

## 五、现代存储技术

### NVMe 协议

早期 SSD 沿用 **SATA** 接口（为 HDD 设计），成为性能瓶颈：

| 接口 | 带宽 | 协议 | 队列深度 | 说明 |
|:---|:---|:---|:---|:---|
| **SATA** | 6 Gbps（约 550 MB/s） | AHCI | 1 队列 × 32 命令 | HDD 时代的接口 |
| **NVMe** | PCIe 直连 | NVMe | **最多 64K 队列 × 64K 命令** | 为闪存设计 |

**NVMe 的关键优势**：

- **高队列深度**：SATA/AHCI 只有 1 个队列 32 条命令，无法发挥 SSD 的并发能力；NVMe 支持海量并行队列。
- **低延迟**：绕过 AHCI 的存储栈开销，直接从 PCIe 访问。
- **PCIe 带宽**：PCIe 4.0 x4 可达约 8 GB/s，PCIe 5.0 翻倍。

> **结论**：SSD 的性能不仅取决于闪存，**接口和协议同样关键**——SATA SSD 和 NVMe SSD 的差距可达数十倍。

### 其他存储介质

| 介质 | 特点 | 适用场景 |
|:---|:---|:---|
| **eMMC / UFS** | 移动设备存储标准 | 手机、嵌入式 |
| **Optane（傲腾）** | 3D XPoint 技术，**接近内存的延迟** | 持久内存、缓存（Intel 已停产） |
| **SLC 缓存** | TLC/QLC 盘中划出一块 SLC 区域做写入缓冲 | 提升突发写入性能 |
| **持久内存（PMEM）** | 内存接口的持久存储 | 数据库、内存计算 |

## 六、面试常见问题

**1. 磁盘调度算法在 SSD 上还需要吗？**

**基本不需要**。调度的前提是「寻道开销大」，而 SSD 无机械部件，随机访问延迟与顺序访问接近，排序请求带不来收益。Linux 对 SSD 常使用 `none` 或 `mq-deadline` 调度器。SSD 的性能优化重心是 **FTL、GC、TRIM、队列深度**。

**2. 为什么 SSD 不能做碎片整理？**

碎片整理会产生**大量随机写**，加剧 GC 和写放大，消耗 P/E 次数，**纯粹有害无益**。而且 SSD 的随机访问性能本来就接近顺序访问，整理也没有收益。

**3. 什么是写放大？为什么会产生？**

写放大 = 实际写入闪存量 / 主机请求写入量。

产生原因是闪存「异地更新 + 块级擦除」：修改数据时不能原地覆盖，需写入新页并标记旧页无效；当无效页积累到一定程度，GC 需要搬移有效页并擦除整个块，这个「搬移」就是额外的写入。

**4. TRIM 的作用是什么？不做会怎样？**

TRIM 让操作系统在删除数据时**主动通知 SSD 哪些数据失效**。

不做 TRIM 时，SSD 不知道删除操作，GC 仍会把已失效的数据当作有效数据搬移，**白白增加写放大**，导致性能和寿命下降。

**5. SSD 的寿命怎么算？**

看 **TBW**（Total Bytes Written，总写入量）或 **DWPD**（Drive Writes Per Day，每日全盘写入次数）。

寿命由闪存 P/E 次数决定，**容量越大寿命越长**（写入可分摊到更多块）。

**6. 为什么 SSD 用久了会掉速？**

两个原因：

- **GC 压力增大**：无效页增多，GC 频繁触发。
- **空闲块不足**（尤其接近满盘时）：GC 没有腾挪空间，需要「搬移 + 擦除」的同步操作，延迟大幅上升。

**恢复方法**：执行 TRIM（`fstrim`）、保留充足空闲空间、避免满盘。

**7. SATA SSD 和 NVMe SSD 差在哪？**

**差在接口协议，不在闪存本身**。

SATA SSD 受限于 AHCI（1 队列 × 32 命令）和 6 Gbps 带宽，无法发挥闪存的并发能力；NVMe 走 PCIe 直连，支持海量并行队列和更高带宽，延迟更低、IOPS 更高。

**8. 为什么 HDD 时代强调「顺序写」，SSD 时代还重要吗？**

**仍然重要，但原因变了**：

- HDD 时代：顺序写避免了寻道开销（**延迟问题**）。
- SSD 时代：顺序写减少无效页产生，**降低 GC 频率和写放大**（**寿命与带宽问题**）。

所以底层存储引擎（如数据库的 WAL）依然倾向顺序写，但动机从「减少寻道」变成了「减少写放大」。
