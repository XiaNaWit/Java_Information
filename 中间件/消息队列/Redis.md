# Redis

## 一、Redis 能做消息队列吗？

**能，但要看场景**。Redis 提供了三种实现消息队列的方式，能力差异很大：

| 方案 | 引入版本 | 定位 | 现状 |
|:---|:---|:---|:---|
| **List** | 1.0 | 最简单的队列 | 功能弱，缺陷多 |
| **Pub/Sub** | 2.0 | 发布订阅（广播） | **消息不持久化**，不适合做 MQ |
| **Stream** | **5.0** | **专为消息队列设计** | **推荐方案** |

**核心结论**：

- 如果只是**轻量级、可容忍丢消息**的场景（如内部通知、简单异步任务），Redis 足够用。
- 如果是**核心业务、要求不丢消息、需要可靠投递**，应该用专业的 MQ（Kafka、RocketMQ、RabbitMQ）。
- **Redis 5.0 的 Stream 大幅改善了 List 的缺陷**，但仍有其边界（见第六节）。

## 二、方案一：List 实现

### 基本原理

利用 List 的**阻塞式弹出**特性，实现最基础的队列：

```bash
# 生产者：从左边插入（LPUSH）
LPUSH queue:task "task1"
LPUSH queue:task "task2"

# 消费者：从右边取出（RPOP），先进先出
RPOP queue:task        # 得到 task1
```

**为什么是 `LPUSH` + `RPOP`**：左进右出，保证**先进先出（FIFO）**。

也可以用 `RPUSH` + `LPOP`（右进左出），效果等价。

### 改进：阻塞式消费

`RPOP` 是非阻塞的——队列为空时立即返回 null。消费者需要**轮询**，浪费 CPU 且有空转延迟。

用 **`BRPOP`**（Blocking RPOP）改进，队列为空时阻塞等待：

```bash
# 阻塞等待，超时时间 0 表示永久阻塞
BRPOP queue:task 0
```

> **实践建议**：用 `BRPOP` 而非 `RPOP` + 轮询，避免无效空转。

### 改进：可靠队列（RPOPLPUSH）

**问题**：`RPOP` 一出队，消息就从 List 中**永久删除**。如果消费者处理到一半崩溃，消息就丢了。

**解决**：用 `RPOPLPUSH`（或 6.2+ 的 `LMOVE`）把消息**同时**从原队列移到一个「处理中队列（备份队列）」：

```bash
# 原子操作：从 queue:task 取出，同时放入 queue:task:processing
RPOPLPUSH queue:task queue:task:processing
```

消费者处理流程：

```text
① RPOPLPUSH 取出消息，消息进入 processing 队列（不丢失）
② 处理业务逻辑
③ 处理成功 → LREM 从 processing 队列删除该消息
④ 处理失败/进程崩溃 → 消息仍在 processing 队列中
⑤ 定时任务扫描 processing 队列，把超时未确认的消息重新投递回原队列
```

**这就是「可靠队列」的基本思路**——用一个备份队列模拟「未确认」状态。

> ⚠️ **注意**：这仍不是真正的可靠投递。因为第 ③ 步「从 processing 删除」如果失败，消息会被**重复投递**——所以业务必须做**幂等**处理。
>
> Redis 官方文档也明确说：这个方案提供的是「至少一次（at-least-once）」语义，**不保证不重复**。

### List 方案的不足

| 不足 | 说明 |
|:---|:---|
| **消息持久化不可靠** | Redis 是内存数据库，RDB/AOF 只是辅助手段。服务器宕机时**一定会丢失一部分数据**，对很多业务无法接受 |
| **热 key 性能问题** | 无论用 Codis 还是 Twemproxy 集群方案，对同一队列的读写**最终都会落到同一台实例**，且**无法通过扩容解决**。并发极高时形成无法解决的热 key，严重可致系统崩溃 |
| **没有确认机制** | `RPOP` 后消息立即从 List 删除。消费者失败时消息无法找回。虽然可以让消费者失败时重新投递，但**万一消费者进程被 `kill -9`、panic、coredump 呢**？消息就彻底丢了 |
| **不支持多订阅者** | 一条消息只能被一个消费者消费，`RPOP` 之后就没了。如果队列中存的是日志，监控系统要消费它做报警、BI 系统要消费它画报表、链路追踪要消费它画调用关系——**这种「一份消息多方消费」的场景 List 无法支持** |
| **不支持二次消费** | 消息 `RPOP` 后就没了。如果消费者程序跑了一半发现代码有 bug，修复后想**从头再消费一次**就不可能了 |
| **无消费者组概念** | 无法在多个消费者间做负载均衡，也无法记录消费进度 |

> **为什么「热 key」无法通过扩容解决**：因为 List 是**单 key 结构**，一个 key 只能位于一个 Redis 节点上。无论集群有多少节点，对这个队列的读写都压在同一个节点。这是 Redis 集群方案的固有局限。

## 三、方案二：Pub/Sub 发布订阅

### 基本原理

Redis 2.0 引入的发布订阅模式，是**广播式**的消息传递：

```bash
# 消费者订阅频道
SUBSCRIBE channel:news

# 生产者发布消息
PUBLISH channel:news "hello"

# 支持模式订阅（通配符）
PSUBSCRIBE news.*
```

**特点**：

- **一对多广播**：一条消息会**同时**被所有订阅者收到（解决了 List 不支持多订阅者的问题）。
- **无持久化**：消息发布后立即转发给当前在线的订阅者，**不存储**。

### 致命的缺点：消息不持久化

**这是 Pub/Sub 和阿克琉斯之踵**：

| 问题 | 说明 |
|:---|:---|
| **消息不存储** | 发布时若无订阅者，消息**直接丢弃** |
| **订阅者断线即丢** | 订阅者掉线重连期间的消息**全部丢失** |
| **无 ACK 机制** | 无法确认消费，无法重投 |
| **无消费进度** | 无法记录消费到哪，无法回溯 |

**结论**：`Pub/Sub` **只适合「允许丢失」的实时通知场景**（如配置变更推送、哨兵通知），**绝不适合做业务消息队列**。

> 这也是为什么 Redis 5.0 要引入 Stream——Pub/Sub 的不可靠性决定了它无法承担 MQ 职责。

## 四、方案三：Stream（推荐）

### 为什么引入 Stream

List 和 Pub/Sub 的缺陷可以归纳为两类：

- **List**：有序、可阻塞，但**无确认机制、无法多播、无消费进度**。
- **Pub/Sub**：广播好，但**不持久化、无确认、无进度**。

**Stream（Redis 5.0）** 就是为了**同时解决这两类问题**而设计的，可以理解为「Redis 版的 Kafka」：

```text
Stream = 持久化的消息日志 + 消费者组 + ACK 确认 + 消费进度
```

### 核心概念

| 概念 | 说明 |
|:---|:---|
| **Entry（消息）** | 每条消息有一个**唯一 ID**，格式 `时间戳-序号`（如 `1696666666666-0`） |
| **Stream** | 消息的有序日志，消息**持久保存**在内存（可配 AOF/RDB） |
| **Consumer Group（消费者组）** | 组内多个消费者**竞争消费**，实现负载均衡 |
| **Consumer（消费者）** | 组内成员，各自维护消费进度 |
| **PEL（Pending Entries List）** | 已投递但**未 ACK** 的消息列表，用于故障恢复 |
| **last_delivered_id** | 流的投递位置游标 |

### 基本命令

```bash
# 生产消息（* 表示自动生成 ID）
XADD mystream * name "张三" age 18
# 输出：1696666666666-0

# 查看消息数量
XLEN mystream

# 读取消息（从开头读 10 条）
XREAD COUNT 10 STREAMS mystream 0

# 阻塞读取（类似 BRPOP）
XREAD BLOCK 0 STREAMS mystream $

# 范围查询
XRANGE mystream - +
```

### 消费者组

**创建消费者组**：

```bash
# 从 Stream 开头开始消费（$ 表示从最新位置开始）
XGROUP CREATE mystream group1 0
```

**组内消费**：

```bash
# > 表示读取「从未投递过的新消息」
XREADGROUP GROUP group1 consumer1 COUNT 10 STREAMS mystream >
```

**Consumer Group 的工作方式**：

```text
mystream（消息流）
   ↓ 同一组内的消息被瓜分
group1
 ├── consumer1  ← 分到一部分消息
 ├── consumer2  ← 分到另一部分
 └── consumer3  ← 分到剩下的

group2  ← 不同组之间互不影响，各自收到全量消息
```

**关键特性**：

- **组内竞争**：同一条消息只会被组内**一个**消费者消费（负载均衡）。
- **组间独立**：不同消费者组各自维护进度，**都能收到全量消息**（满足「多方消费」需求）。

### ACK 确认机制

**Stream 的核心优势**——消息读取后进入 **PEL（待确认列表）**，直到显式 ACK 才移除：

```bash
# 消费一条消息
XREADGROUP GROUP group1 consumer1 COUNT 1 STREAMS mystream >
# 返回：1696666666666-0

# 处理成功 → 确认
XACK mystream group1 1696666666666-0
```

**故障恢复流程**：

```text
① 消费者读取消息 → 消息进入 PEL（标记为「已投递未确认」）
② 处理业务
③ 成功 → XACK 移除
④ 消费者崩溃 → 消息仍在 PEL 中
⑤ 另一个消费者用 XAUTOCLAIM / XPENDING 接管这些消息 → 重新处理
```

**查看和接管未确认消息**：

```bash
# 查看待确认消息
XPENDING mystream group1

# 接管超时未确认的消息（Redis 6.2+）
XAUTOCLAIM mystream group1 consumer2 60000 0

# 旧版本用 XCLAIM
XCLAIM mystream group1 consumer2 60000 1696666666666-0
```

> **这实现了「至少一次（at-least-once）」投递语义**——消息不会因消费者崩溃而丢失，但可能被重复处理（所以业务仍需**幂等**）。

### Stream 如何解决 List 的缺陷

| List 的缺陷 | Stream 的解法 |
|:---|:---|
| 无确认机制 | ✅ **PEL + XACK**，未确认不删除 |
| 不支持多订阅者 | ✅ **多个消费者组**，各自独立消费全量 |
| 不支持二次消费 | ✅ 消息**持久保存**，可通过 `XRANGE` 回溯历史 |
| 无消费进度 | ✅ 每组维护 `last_delivered_id` |
| 热 key | ⚠️ **仍存在**（Stream 同样是单 key 结构） |
| 持久化不可靠 | ⚠️ **仍存在**（仍依赖 RDB/AOF） |

> **注意**：Stream 解决了「应用层」的大部分缺陷，但**热 key 和持久化这两个底层问题依然存在**——它们源于 Redis 的单 key 结构与内存数据库本质，不是 Stream 能解决的。

## 五、三种方案对比

| 对比维度 | List | Pub/Sub | Stream |
|:---|:---|:---|:---|
| **引入版本** | 1.0 | 2.0 | **5.0** |
| **消息持久化** | ⚠️ 出队即删 | ❌ 不存 | ✅ 持久保存 |
| **多订阅者** | ❌ | ✅ 广播 | ✅ 多消费者组 |
| **ACK 确认** | ❌ | ❌ | ✅ PEL |
| **消费进度** | ❌ | ❌ | ✅ |
| **二次消费** | ❌ | ❌ | ✅ |
| **阻塞消费** | ✅ BRPOP | ✅ SUBSCRIBE | ✅ XREAD BLOCK |
| **消息回溯** | ❌ | ❌ | ✅ |
| **热 key** | ⚠️ 有 | ⚠️ 有 | ⚠️ 有 |
| **适用场景** | 极简队列 | 实时通知 | **可靠消息队列** |

## 六、Redis 不适合做消息队列的场景

即使有 Stream，Redis 做 MQ 仍有**两个底层硬伤**（这也是面试常考的「为什么不用 Redis 做 MQ」）：

**1. 持久化与可靠性不足**

Redis 是**内存数据库**，虽然提供 RDB（快照）和 AOF（日志）两种持久化，但：

| 机制 | 问题 |
|:---|:---|
| **RDB** | 定期快照，两次快照之间的数据**必然丢失** |
| **AOF** | 默认 `everysec`（每秒刷盘），最多丢 1 秒数据；即使 `always` 也无法应对主从切换的数据丢失 |

**主从复制的异步性**：主节点收到写入后**立即返回**，从节点异步复制。如果主节点在同步完成前宕机，且发生主从切换，**已确认的消息可能丢失**。

> 对比 Kafka：通过**多副本 ISR 机制 + acks=all** 可以实现真正的「不丢消息」。Redis 的异步复制机制做不到。

**2. 热 key 与扩展性**

无论 List 还是 Stream，**都是单 key 结构**：

- 一个 key 只能落在**一个 Redis 节点**上。
- 对同一队列的读写**无法通过增加节点分摊**。
- 高并发下形成**无法解决的热 key**，严重时导致节点崩溃。

> **缓解思路**：把队列**分片**（如 `queue:task:0` ~ `queue:task:9`，生产者按 hash 投递）。但这增加了复杂度，且消费端也要处理分片，本质是「用复杂度换扩展性」。

**3. 其他不足**

| 不足 | 说明 |
|:---|:---|
| **消息堆积能力弱** | 内存容量有限，大量堆积会 OOM（Kafka 可落磁盘堆积） |
| **无消息重试/死信队列** | 需要自己在应用层实现 |
| **无事务消息** | 不支持「本地事务 + 消息」的原子性（RocketMQ 有） |
| **无延迟消息** | 原生不支持定时/延迟投递（需借助 ZSet 自己实现） |
| **无消息过滤** | Kafka/RocketMQ 支持按 Tag/SQL 过滤 |

## 七、什么时候可以用 Redis 做消息队列

**适合用 Redis 的场景**：

| 场景 | 说明 |
|:---|:---|
| **轻量级异步任务** | 如发送邮件、生成缩略图，允许少量丢失 |
| **低延迟要求** | Redis 延迟在亚毫秒级，远优于 Kafka 的毫秒级 |
| **已有 Redis 基建** | 不想为小需求引入一个新的 MQ 组件 |
| **消息量不大** | 内存能装下，不会大量堆积 |
| **内部通知/告警** | 允许丢失的实时通知（甚至可用 Pub/Sub） |

**应该用专业 MQ 的场景**：

| 场景 | 推荐 |
|:---|:---|
| **核心业务、不能丢消息** | RocketMQ / Kafka |
| **海量日志、大数据管道** | Kafka |
| **复杂路由、死信队列** | RabbitMQ |
| **需要事务消息** | RocketMQ |
| **需要消息回溯、长堆积** | Kafka |

**选型决策**：

```text
需要「绝不丢消息」或「海量堆积」？
  ├── 是 → 用专业 MQ（Kafka / RocketMQ / RabbitMQ）
  └── 否 → 消息量小、延迟敏感、已有 Redis 基建？
            ├── 是 → 可以用 Redis Stream
            └── 否 → 也建议用专业 MQ（避免后期迁移成本）
```

> **一句话总结**：**Redis 可以做消息队列，但它的定位是「轻量级、低延迟、可容忍少量丢失」的场景**。Stream 让它比 List 可靠得多，但**持久化和热 key 这两个底层限制决定了它无法替代专业 MQ**。
