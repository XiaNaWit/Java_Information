1. **生产环境如何排查慢SQL**

    - 开启慢日志：设置 long_query_time=1（或0.1秒），开启 log_queries_not_using_indexes。
    
    - 实时抓取：用 performance_schema 的 events_statements_current 表查看当前执行中的SQL。
    
    - 分析工具：用 pt-query-digest 分析慢日志聚合排名；用 EXPLAIN 查看执行计划，重点关注 type（ALL/ref）、rows 和 Extra（Using filesort）。



2. **哪些场景会触发表锁而非行锁**

   - InnoDB中行锁是基于索引实现的，未走索引的更新/删除会锁全表（实际是逐行加锁但退化为表级效果）。此外，显式 LOCK TABLES、DDL操作（如ALTER）、MyISAM引擎、以及可重复读隔离级别下间隙锁范围过大时也可能导致锁范围膨胀。


3. **线上大量表锁阻塞，如何快速定位引发问题的慢SQL**

    - 查当前锁：show engine innodb status 看 LATEST DETECTED DEADLOCK 和事务列表。
    
    - 找源头：查询 information_schema.innodb_trx，按 trx_started 排序，找到执行时间最长且状态为 RUNNING 的事务，关联 processlist 获取对应SQL。
    
    - 杀手锏：开启 performance_schema 的 metadata_locks 表，直接定位持有未提交锁的线程ID，必要时 kill。


4. **三张表联查超时，除加索引外的优化思路**
    
    - SQL写法：将多表JOIN拆成多次单表查询，在应用层组装；或使用子查询预先过滤小表结果集（驱动表尽量是小表）；避免 SELECT *，只取必需字段。
    
    - 表结构：考虑冗余字段（反范式化）减少JOIN；或创建汇总中间表定时计算；也可将冷热数据分离，缩小单表数据量。


5. **生产环境是否使用联表查询**

   - 分场景。OLTP高并发核心链路尽量避免（建议拆分为多次查询+缓存）；OLAP报表或管理后台，在数据量可控且索引完备前提下适度使用，并设置超时阈值。


6. **生产中联表查询的潜在风险**

    - 数据库CPU/IO飙升，影响整体稳定性。
    
    - 执行计划选错驱动表或索引，导致全表扫描。
    
    - 跨库或分库分表下无法JOIN，需改架构。
    
    - 事务中长JOIN会持有锁，增大死锁和主从延迟风险。


7. **线上大事务的危害**

    - 长时间持有锁，阻塞其他DML，引发业务超时。
    
    - 回滚时需大量Undo日志，导致数据库抖动。
    
    - 导致主从延迟加剧（从库需重放大量Binlog）。
    
    - 容易触发死锁，且排查困难。


8. **如何识别大事务**

    - 查询 information_schema.innodb_trx，关注 trx_started（运行超过几秒）、trx_rows_modified（修改行数大）、trx_lock_time（锁等待时间长）。或开启 performance_schema 监控事务执行时间和影响行数。


9. **拆分大事务的落地手段**

    - 分页循环：将大批量DELETE/UPDATE改为 LIMIT 1000 循环执行，中间加 COMMIT 和短暂 SLEEP。
    
    - 按主键范围：按ID范围分段，每次处理一段。
    
    - 业务拆分：将多个写操作拆成独立小事务，或使用消息队列异步削峰。


10. **生产环境死锁排查流程**

    - 执行 show engine innodb status 查看 LATEST DETECTED DEADLOCK，获取事务1和2的SQL与持有的锁。
    
    - 开启 innodb_print_all_deadlocks=ON，将死锁信息记录到错误日志。
    
    - 分析两条SQL的加锁顺序（如更新主键与更新二级索引的顺序相反）。

11. **通用死锁解决方案**

    - 核心：统一多个事务的访问顺序（如都按主键ID升序更新）。
    
    - 将隔离级别降为 READ COMMITTED（减少间隙锁）。
    
    - 在索引上尽量使用等值匹配，缩小锁粒度。
    
    - 应用层捕获死锁异常（DeadlockLoserDataAccessException）并重试。


12. **按创建时间分片且有索引，分页越靠后查询越慢的原因**

    - LIMIT 100000, 10 即使有索引，也需要扫描并丢弃前10万条数据（索引叶子节点遍历+回表），MySQL无法直接跳过OFFSET，导致大量随机IO。


13. **上述分页慢的优化方案**

    - 延迟关联（覆盖索引）：先查子查询获取主键ID（SELECT id FROM t WHERE time>xxx ORDER BY time LIMIT 100000,10），再回表联查完整数据。

    - 游标/书签：记录上一页最后一条的 time 和 id，下一页用 WHERE (time,id) > (?,?) LIMIT 10。


14. **大表实时count统计超时的替代方案**

    - 使用汇总表（每日/每小时预聚合）或 Redis 维护实时计数。
    
    - 若允许误差，查 information_schema.tables 获取估算行数。
    
    - 对非精确要求，使用 EXPLAIN 的 rows 估值。


15. **高频写入主库压力大、从库SQL堆积，批量写入如何限流**

    - 应用层：使用信号量或令牌桶限制并发插入数；将单条INSERT改为批量（如每批1000条）减少事务次数。
    
    - 数据库层：调整 sync_binlog 和 innodb_flush_log_at_trx_commit 牺牲部分持久性换吞吐（从库异常时暂停写入）。
    
    - 架构：引入MQ做缓冲，或写入日志文件后由独立程序批量加载。


16. **字段有索引但未命中走全表扫描的诱因与解决办法**

    - 诱因：隐式类型转换（varchar字段传数字）、索引列参与运算（where col+1=5）、使用函数包裹（where date(col)=...）、!= 或 is null（视版本）、或优化器认为全表扫描更快（数据量小）。
    
    - 解决：规范SQL写法，用 FORCE INDEX 验证（临时），或 ANALYZE TABLE 更新统计信息。
