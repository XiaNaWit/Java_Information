1. **生产环境如何排查慢SQL**

    - 开启慢日志：设置 long_query_time=1（或0.1秒），开启 log_queries_not_using_indexes。
    
    - 实时抓取：用 performance_schema 的 events_statements_current 表查看当前执行中的SQL。
    
    - 分析工具：用 pt-query-digest 分析慢日志聚合排名；用 EXPLAIN 查看执行计划，重点关注 type（ALL/ref）、rows 和 Extra（Using filesort）。



2. **哪些场景会触发表锁而非行锁**

   - InnoDB中行锁是基于索引实现的，未走索引的更新/删除会锁全表（实际是逐行加锁但退化为表级效果）。此外，显式 LOCK TABLES、DDL操作（如ALTER）、MyISAM引擎、以及可重复读隔离级别下间隙锁范围过大时也可能导致锁范围膨胀。


3. **线上大量表锁阻塞，如何快速定位引发问题的慢SQL**

    - 查当前锁：show engine innodb status 看 LATEST DETECTED DEADLOCK 和事务列表。
    
    - 找源头：查询 information_schema.innodb_trx，按 trx_started 排序，找到执行时间最长且状态为 RUNNING 的事务，关联 processlist 获取对应SQL。
    
    - 杀手锏：开启 performance_schema 的 metadata_locks 表，直接定位持有未提交锁的线程ID，必要时 kill。


4. **三张表联查超时，除加索引外的优化思路**
    
    - SQL写法：将多表JOIN拆成多次单表查询，在应用层组装；或使用子查询预先过滤小表结果集（驱动表尽量是小表）；避免 SELECT *，只取必需字段。
    
    - 表结构：考虑冗余字段（反范式化）减少JOIN；或创建汇总中间表定时计算；也可将冷热数据分离，缩小单表数据量。


5. **生产环境是否使用联表查询**

   - 分场景。OLTP高并发核心链路尽量避免（建议拆分为多次查询+缓存）；OLAP报表或管理后台，在数据量可控且索引完备前提下适度使用，并设置超时阈值。


6. **生产中联表查询的潜在风险**

    - 数据库CPU/IO飙升，影响整体稳定性。
    
    - 执行计划选错驱动表或索引，导致全表扫描。
    
    - 跨库或分库分表下无法JOIN，需改架构。
    
    - 事务中长JOIN会持有锁，增大死锁和主从延迟风险。


7. **线上大事务的危害**

    - 长时间持有锁，阻塞其他DML，引发业务超时。
    
    - 回滚时需大量Undo日志，导致数据库抖动。
    
    - 导致主从延迟加剧（从库需重放大量Binlog）。
    
    - 容易触发死锁，且排查困难。


8. **如何识别大事务**

    - 查询 information_schema.innodb_trx，关注 trx_started（运行超过几秒）、trx_rows_modified（修改行数大）、trx_lock_time（锁等待时间长）。或开启 performance_schema 监控事务执行时间和影响行数。


9. **拆分大事务的落地手段**

    - 分页循环：将大批量DELETE/UPDATE改为 LIMIT 1000 循环执行，中间加 COMMIT 和短暂 SLEEP。
    
    - 按主键范围：按ID范围分段，每次处理一段。
    
    - 业务拆分：将多个写操作拆成独立小事务，或使用消息队列异步削峰。


10. **生产环境死锁排查流程**

    - 执行 show engine innodb status 查看 LATEST DETECTED DEADLOCK，获取事务1和2的SQL与持有的锁。
    
    - 开启 innodb_print_all_deadlocks=ON，将死锁信息记录到错误日志。
    
    - 分析两条SQL的加锁顺序（如更新主键与更新二级索引的顺序相反）。

11. **通用死锁解决方案**

    - 核心：统一多个事务的访问顺序（如都按主键ID升序更新）。
    
    - 将隔离级别降为 READ COMMITTED（减少间隙锁）。
    
    - 在索引上尽量使用等值匹配，缩小锁粒度。
    
    - 应用层捕获死锁异常（DeadlockLoserDataAccessException）并重试。


12. **按创建时间分片且有索引，分页越靠后查询越慢的原因**

    - LIMIT 100000, 10 即使有索引，也需要扫描并丢弃前10万条数据（索引叶子节点遍历+回表），MySQL无法直接跳过OFFSET，导致大量随机IO。


13. **上述分页慢的优化方案**

    - 延迟关联（覆盖索引）：先查子查询获取主键ID（SELECT id FROM t WHERE time>xxx ORDER BY time LIMIT 100000,10），再回表联查完整数据。

    - 游标/书签：记录上一页最后一条的 time 和 id，下一页用 WHERE (time,id) > (?,?) LIMIT 10。


14. **大表实时count统计超时的替代方案**

    - 使用汇总表（每日/每小时预聚合）或 Redis 维护实时计数。
    
    - 若允许误差，查 information_schema.tables 获取估算行数。
    
    - 对非精确要求，使用 EXPLAIN 的 rows 估值。


15. **高频写入主库压力大、从库SQL堆积，批量写入如何限流**

    - 应用层：使用信号量或令牌桶限制并发插入数；将单条INSERT改为批量（如每批1000条）减少事务次数。
    
    - 数据库层：调整 sync_binlog 和 innodb_flush_log_at_trx_commit 牺牲部分持久性换吞吐（从库异常时暂停写入）。
    
    - 架构：引入MQ做缓冲，或写入日志文件后由独立程序批量加载。


16. **字段有索引但未命中走全表扫描的诱因与解决办法**

    - 诱因：隐式类型转换（varchar字段传数字）、索引列参与运算（where col+1=5）、使用函数包裹（where date(col)=...）、!= 或 is null（视版本）、或优化器认为全表扫描更快（数据量小）。
    
    - 解决：规范SQL写法，用 FORCE INDEX 验证（临时），或 ANALYZE TABLE 更新统计信息。
     TiDB、OceanBase、PolarDB-HTAP（阿里云）、Greenplum（偏向AP），以及 ClickHouse（配合TP库做AP查询）。


17. **订单表单表 8000 万行，按用户ID查最近订单已经开始超时，怎么判断该不该分库分表**

   - 先排除「伪瓶颈」：单表大不等于必须分表。用 EXPLAIN 确认查询是否走索引、是否回表过多、是否 SELECT * 拉了无用字段。
   
   - 依次尝试更轻的手段：SQL 与索引优化 → 冷热数据归档（把一年前的订单迁到历史库）→ 加 Redis 缓存 → 加从库做读写分离。
   
   - 判断需要分表的信号：
   
     - 归档 + 优化后单表仍是千万级以上，且 B+树从 3 层升到 4 层，查询明显变慢。
     
     - 写入并发高，单库 QPS 逼近 1000～2000 的瓶颈。
     
     - 磁盘容量或 IOPS 已到上限，无法靠升级硬件解决。
   
   - 结论：分库分表是最后手段，一旦拆分会永久增加 JOIN、事务、运维成本，能用归档 + 缓存顶住就不要拆。


18. **订单表要分库分表，按订单ID分片还是按用户ID分片**

   - 场景矛盾：订单ID分片写入最均匀；但业务上最高频的查询是「查我的订单」，若按订单ID分片，这个查询要扫全部分片再聚合，性能极差。
   
   - 结论：按「用户ID」分片。分片键的选择标准是「让核心查询能命中单一分片」，而不是让数据最均匀。
   
   - 但副作用是：按订单ID查详情、商家按订单查询会变成跨分片查询。
   
   - 解决：建「订单ID → 用户ID」的映射表（或把 userId 编入订单号），先定位分片再查询；商家维度的查询另建一张按商家ID分片的冗余表。
   
   - 经验：分片键一旦确定几乎无法更改，必须按「最核心的查询路径」来定，其余查询用冗余或映射表补齐。


19. **分片键选错了，导致大量查询要广播到所有分片，线上 CPU 打满怎么办**

   - 定位：开启慢日志 + 监控分片路由日志，找出哪些 SQL 没带上分片键（如按订单ID查、按状态查、按时间范围查）。
   
   - 短期止血：把这类查询限流或加超时；对高频的「订单ID查询」增加「订单ID → 用户ID」本地缓存，减少跨分片扫描。
   
   - 长期治理：按查询维度补建冗余表。例如原表按 userId 分片，再建一张按 orderId 分片的索引表，只存路由所需的最小字段（orderId、userId、分片位）。
   
   - 兜底：确实无法避免的聚合类查询（如按状态统计总量）交给 ES 或数仓做，不查 MySQL 分片。


20. **分库分表后，运营要查「全部订单列表 + 按金额排序 + 每页 20 条」，怎么实现**

   - 问题：`ORDER BY amount LIMIT 20 OFFSET 10000` 要在每个分片上都取前 10020 条，归并后再排序，越翻页越慢，且内存占用高。
   
   - 方案一（内存归并）：各分片取 `LIMIT offset+limit` 条，应用层归并排序后截取。数据量小可用，翻页深时不可行。
   
   - 方案二（二次查询法）：先各分片取 `offset/n + limit` 条，取结果中的最小值 min，再用 `WHERE amount >= min` 各分片重查，归并得到准确结果。适合 offset 较大的场景。
   
   - 方案三（游标分页）：业务上改成「下一页」模式，记录上一页最后的 (amount, id)，下一页用 `WHERE (amount,id) > (?,?) LIMIT 20`，彻底绕开 OFFSET。
   
   - 方案四（换存储）：这类多维排序 + 深分页的运营需求，直接同步到 Elasticsearch 查询，MySQL 只承担按分片键的点查。


21. **营销活动要生成全局唯一订单号，分库分表后自增主键失效了，怎么选**

   - UUID：本地生成无网络开销，但无序——会导致 B+树随机插入、页分裂严重，且占 36 字节，不适合做主键。
   
   - 数据库自增 + 步长：多库设置不同起始值和步长（如 3 库分别 1/2/3 起步、步长 3）。实现简单，但库数量固定后难以扩容。
   
   - 号段模式：应用一次从 DB 批量取 1000 个 ID 缓存在内存，用完再取。性能高，但强依赖 DB 可用性。
   
   - 雪花算法：64 位 = 1 符号位 + 41 时间戳 + 10 机器ID + 12 序列号，趋势递增、性能高、不依赖 DB。**风险是时钟回拨会产生重复 ID**。
   
   - 落地建议：优先用美团 Leaf（号段 + 雪花双模式，已解决时钟回拨）、百度 UidGenerator；或直接用 ShardingSphere 内置的分布式 ID 生成器。
   
   - 注意：ID 必须趋势递增。无序 ID 在高并发写入时会因页分裂拖垮性能。


22. **下单成功后要同时扣减「用户库」的余额和「订单库」的库存，跨库事务怎么保证**

   - 首要原则：通过分片键设计让关联数据落在同一分片（如按 userId 同时分库订单和余额），从根上避免跨库事务。
   
   - 若无法避免，按一致性要求分档选方案：
   
     - 强一致（XA / 2PC）：性能差、协调者阻塞风险高，生产环境基本不用。
     
     - TCC（Try-Confirm-Cancel）：业务层实现预留/确认/取消三步，灵活但侵入性极强，适合金融核心链路。
     
     - SAGA：把长事务拆成多个本地事务 + 补偿操作，适合流程长、步骤多的业务。
     
     - 本地消息表 / 事务消息（RocketMQ）：先落本地事务 + 消息表，再由 MQ 异步驱动下游，实现最终一致。
   
   - 实践选型：绝大多数互联网下单场景用「本地消息表 + MQ」；金融核心才上 TCC。前提是下游必须做幂等。


23. **业务量翻倍，4 个库要扩到 5 个库，发现 80% 的数据都要迁移怎么办**

   - 根因：Hash 取模分片下，从 N 扩到 M（非倍数），几乎所有数据的 hash 结果都会变，需要全量搬迁。
   
   - 方案一（翻倍扩容）：只从 N 扩到 2N（如 4→8）。原数据一半留在原库、一半迁到新库，迁移量刚好 50%，路由规则也简单（判断 hash 新增的 1 个 bit）。
   
   - 方案二（一致性 Hash）：环上增减虚拟节点只影响相邻区间的数据，迁移量大幅减少。
   
   - 双写迁移步骤（不停机）：
   
     1. 新库建好，开启双写（写旧库的同时写新库）。
     
     2. 用 DataX 等工具全量迁移历史数据。
     
     3. 订阅 Binlog（Canal）追平增量，并跑数据校验比对一致性。
     
     4. 灰度切读：按用户或比例逐步把读流量切到新库，观察无异常。
     
     5. 读流量全切稳定后，停止双写，下线旧库。
   
   - 经验：**一开始就规划成 2 的幂次（如 4、8、16 库）**，后续只做翻倍扩容，可以避开这个问题。


24. **分库分表后「查询总订单数」和跨 100 个分片的 count 统计超时，怎么优化**

   - 问题：`SELECT COUNT(*)` 和 `GROUP BY` 在分片架构下必须并发查所有分片再汇总，分片越多越慢。
   
   - 方案一（汇总表）：定时任务每 5 分钟/每小时预聚合到一张统计表，查询直接读汇总结果。
   
   - 方案二（Redis 计数）：写入时用 Redis 原子自增维护实时计数，适合「总订单数」这类简单计数。
   
   - 方案三（换存储）：多维度、可组合的统计需求（如按日/按品类/按地区交叉统计）同步到 ClickHouse 或 ES 做 OLAP 查询。
   
   - 方案四（允许误差）：用 EXPLAIN 或 information_schema.tables 的估算行数，适合只是展示「约 xx 万条」的场景。
   
   - 原则：**分片架构下不做实时精确聚合**，改为预计算或异步统计。


25. **从单体 MySQL 迁移到分库分表，怎么保证业务不停机、数据不丢**

   - 阶段一（改造准备）：引入 ShardingSphere 做数据源路由，但先配置成「单库单表」模式上线，验证中间件链路无误。
   
   - 阶段二（建新库 + 双写）：建好分片库表，开启双写旧库和新库。推荐用 ShardingSphere 的「数据双写」或 Canal 订阅 Binlog 写入新库。
   
   - 阶段三（全量 + 增量迁移）：DataX 做存量全量迁移；Canal 订阅增量 Binlog 持续追平，直到延迟归零。
   
   - 阶段四（数据校验）：用 pt-table-checksum 或自研比对工具，逐表逐分片校验行数与关键字段一致性，差异必须清零。
   
   - 阶段五（灰度切读）：先切少量从库读流量或内部用户，观察 SQL 兼容性与性能，再逐步放量。
   
   - 阶段六（切写 + 下线）：读流量全切稳定后切写流量，观察一段时间，停止双写，保留旧库做回滚兜底，最后下线。
   
   - 关键点：每个阶段都要可回滚，双写期间必须保证幂等（用唯一键或去重表）。


26. **选了 ShardingSphere-JDBC 后，发现应用启动变慢、升级要重启几十个服务，该不该换成 Proxy**

   - 这是 Client 层方案的固有代价，需要先看清两类方案的本质差异：
   
     | 对比项 | Client（ShardingSphere-JDBC） | Proxy（MyCat / ShardingSphere-Proxy） |
     |:---|:---|:---|
     | 部署形态 | Jar 包集成在应用内 | 独立进程，应用当普通 MySQL 连 |
     | 性能 | 无网络转发，性能更好 | 多一跳网络，略低 |
     | 运维 | 分散，升级需各应用重启 | 集中，升级只动 Proxy |
     | 语言 | 仅 Java | 多语言透明 |
     | 瓶颈 | 无单点 | Proxy 可能成为瓶颈与单点 |
   
   - 判断标准：Java 技术栈、性能敏感 → 留 Client；多语言、大量小服务、要求运维集中 → 换 Proxy。
   
   - 折中方案：用 ShardingSphere 的治理中心（Zookeeper/Etcd）下发规则，避免每次改分片规则都重启应用。
   
   - 补充：若引入 Proxy，必须对 Proxy 做集群 + 负载均衡，否则它就是新的单点故障。


27. **重写了分页查询后，线上出现部分用户看到重复数据或漏数据，怎么排查**

   - 这是分片分页最典型的坑，常见三个原因：
   
     - 原因一（排序字段不唯一）：只按 `create_time` 排序，多个分片中存在相同时间的数据，归并时顺序不稳定导致重复或漏。**解决办法：排序字段加上唯一键，如 `ORDER BY create_time, id`**。
     
     - 原因二（内存归并截断错误）：各分片取 `LIMIT offset+limit` 后归并，若代码里提前截断就可能漏数据。需确认归并逻辑是「全部排序完再截取」。
     
     - 原因三（二次查询法的边界处理）：二次查询法中 min 值的取值或重查条件写错，会漏掉刚好等于边界的数据，应使用 `>=` 并去重。
   
   - 定位手段：抽取出问题用户的 userId 和分页参数，手动逐个分片执行 SQL，对比归并结果与实际数据的差异。
   
   - 预防：分页查询必须保证「全局唯一且稳定的排序」，这是分片分页的第一原则。


28. **公司订单量没到千万，但老板要求上分库分表，你怎么评估和回答**

   - 先量化现状：给出当前单表行数、QPS、慢查询数量、磁盘与 IOPS 使用率的数据，判断是否真的触及瓶颈。
   
   - 说明分库分表的真实代价：
   
     - 跨库 JOIN 失效，需大量改为冗余字段或应用层组装。
     
     - 分布式事务只能走最终一致，业务要改造幂等与补偿。
     
     - 全局 ID、跨分片分页/排序/聚合全部要重写。
     
     - 运维成本成倍上升：DDL 变更、备份、监控、扩容工作量翻倍。
   
   - 提出更优路径：
   
     - 数据量小、只是查询慢 → 优化 SQL 与索引。
     
     - 读多写少 → Redis 缓存 + 从库读写分离。
     
     - 历史数据占大头 → 冷热分离与归档。
     
     - 怕未来扩展 → 换成 TiDB / OceanBase 这类原生支持水平扩展的 NewSQL，避免自行拆分的复杂度。
   
   - 结论：**没有量就不要拆**。如果确有必要，优先评估 NewSQL 而非自行分库分表。
