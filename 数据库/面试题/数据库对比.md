## 一、关系型 vs 非关系型

| 对比维度 | 关系型（SQL） | 非关系型（NoSQL） |
|:---|:---|:---|
| 数据模型 | 二维表（行 + 列），需预定义 Schema | 键值/文档/列族/图，Schema 灵活 |
| 事务 | 强 ACID，支持多表事务 | 多数为 BASE，部分支持单文档/单行事务 |
| 关联查询 | JOIN，多表关联强 | 通常不支持 JOIN，需应用层组装或冗余 |
| 扩展方式 | 以垂直扩展为主（分库分表较复杂） | 天然水平扩展（分片） |
| 一致性 | 强一致 | 最终一致（可调） |
| 典型场景 | 金融、订单、ERP 等强一致业务 | 缓存、日志、搜索、海量数据、社交 |
| 代表 | MySQL、PostgreSQL、Oracle | Redis、MongoDB、HBase、ES |

> **选型原则**：需要强事务、复杂关联查询选关系型；需要极高并发读写、海量数据、灵活 Schema 或特定能力（搜索/缓存）选非关系型。实际系统通常是「关系型 + 非关系型」混合使用。

## 二、主流关系型数据库横向对比

### 总览对比

| 对比维度 | MySQL | PostgreSQL | Oracle | SQL Server |
|:---|:---|:---|:---|:---|
| 开源/商业 | 开源（GPL）+ 商业版 | 开源（BSD 类宽松协议） | 闭源商业 | 闭源商业（有 Express 免费版） |
| 所属公司 | Oracle | PostgreSQL 社区 | Oracle | 微软 |
| 定位 | 轻量、易用、Web 首选 | 功能全面、最接近 Oracle 的开源库 | 企业级、功能最全 | 微软生态集成 |
| SQL 标准符合度 | 较低，方言多 | 高（SQL:2023 强制特性覆盖 170/177） | 较高，方言多（PL/SQL） | 较高，方言为 T-SQL |
| 存储引擎 | 插件式（InnoDB 默认，MyISAM 等） | 单一引擎（堆表 + 索引） | 单一引擎 | 单一引擎 |
| 并发模型 | 多线程 | 多进程（每个连接 fork 一个进程） | 多进程 | 多线程 |
| MVCC | InnoDB 支持 | 原生支持，读写互不阻塞 | 原生支持 | 原生支持（含 SNAPSHOT） |
| 默认隔离级别 | REPEATABLE READ | READ COMMITTED | READ COMMITTED | READ COMMITTED |
| 数据类型丰富度 | 一般 | 极丰富（数组、范围、JSONB、几何、自定义） | 丰富（含自定义对象类型） | 丰富 |
| JSON 支持 | 5.7+ JSON，8.0+ 支持多值索引 | JSONB（二进制、可建索引，性能好） | 12c+ 原生 JSON | 2016+ 原生 JSON |
| 索引类型 | B+Tree、Hash、Full-text | B-Tree、Hash、GiST、GIN、BRIN、SP-GiST | B-Tree、位图、函数索引等 | 聚集/非聚集、列存储、全文、空间 |
| 窗口函数 | 8.0+ | 原生支持（含 CTE、递归查询） | 原生支持 | 2005+ 完整支持 |
| 物化视图 | 不支持（需触发器模拟） | 原生支持 | 原生支持 | 支持（索引视图） |
| 复制 | 主从、组复制 | 流复制（物理/逻辑）、同步/异步、PITR | Data Guard、GoldenGate | Always On、日志传送、镜像 |
| 分区表 | 5.1+ 支持 | 原生表分区 | 原生分区 | 原生分区 |
| 学习/运维成本 | 低 | 中 | 高 | 中 |
| 典型场景 | Web 应用、互联网业务 | 复杂查询、分析、GIS、金融 | 大型企业核心系统、银行 | .NET 生态、企业内网系统 |

### MySQL

- **核心优势**：轻量、易上手、生态成熟（云 RDS、中间件、监控工具齐全）、社区庞大。
- **存储引擎**：InnoDB（默认，支持事务、行锁、外键、MVCC）、MyISAM（无事务、表锁，已基本淘汰）。
- **索引**：B+Tree 为主，遵循最左前缀匹配原则；支持覆盖索引、索引下推。
- **事务隔离**：默认 REPEATABLE READ，通过 MVCC + Next-Key Lock 解决幻读。
- **局限**：SQL 标准符合度较低、JSON/高级分析能力弱于 PG、复杂查询优化能力一般。
- **适用**：读多写少的互联网 Web 应用、中小规模业务、快速迭代项目。

### PostgreSQL

- **定位**：功能最强大的开源对象-关系型数据库，常被称作「最接近 Oracle 的开源数据库」。
- **语法与架构**：BSD 类协议可自由使用；支持 C/C++/Java/Python 等多种语言编写存储过程。
- **SQL 标准**：兼容 SQL:2003，SQL:2023 Core 强制特性覆盖度极高（至少 170/177），迁移成本低。
- **数据类型**：除常规类型外，原生支持几何、IP、XML、JSON/JSONB、Range、数组、自定义复合类型。
- **索引能力**：GiST、GIN、SP-GiST、BRIN 等，支持函数索引、部分（行）索引、自定义索引、全文索引。
- **高级特性**：窗口函数、递归 CTE、物化视图、表分区、JIT 编译、FDW（外部数据包装器）。
- **并发与稳定**：多进程架构稳定性高，MVCC 读写互不阻塞；同步复制可保证零数据丢失（可用于金融交易系统）。
- **地理空间**：PostGIS 是行业标准的地理空间扩展，可用 SQL 直接做位置查询。
- **局限**：单机写入性能与简单查询吞吐不及 MySQL（多进程架构、每次查询进程开销较高）；生态工具与人才储备少于 MySQL。
- **适用**：复杂查询与数据分析（OLAP）、高并发写入 + 强一致（金融、订单）、GIS、JSON/半结构化数据、TB～PB 级海量数据。

### Oracle

- **定位**：企业级商业数据库标杆，功能最完整、最成熟。
- **核心特性**：Real Application Clusters（RAC）多节点共享存储集群、Data Guard 容灾、GoldenGate 异构同步、PL/SQL。
- **优势**：极致稳定性与性能、完备的备份恢复与企业级安全、强大的优化器、丰富的诊断工具（AWR/ASH）。
- **劣势**：**闭源收费且极其昂贵**（按 CPU/核心授权）、运维复杂、对硬件资源要求高、轻量场景性价比低。
- **适用**：银行、证券、电信、大型企业核心交易系统等对稳定性和一致性要求极高的场景。
- **补充**：新项目在成本敏感场景下，常用 PostgreSQL 作为 Oracle 的替代方案。

### SQL Server

- **定位**：微软开发的关系型数据库，与 Windows / .NET / Azure / Active Directory 深度集成。
- **平台**：早期仅 Windows，2017+ 支持 Linux 和 Docker。
- **方言**：T-SQL，编程能力强（存储过程、函数、触发器、CTE、窗口函数）。
- **特性**：Always On 可用性组、故障转移集群、SSIS/SSRS/SSAS 套件、列存储索引、行级安全（RLS）、动态数据掩码、始终加密。
- **隔离级别**：支持 6 种（比标准多 SNAPSHOT 和 READ COMMITTED SNAPSHOT 两种基于行版本控制的级别）。
- **版本**：Express（免费，有容量限制）/ Standard / Enterprise。
- **适用**：.NET 技术栈、企业内网系统、报表与 BI 场景。

### 关系型数据库横向选择小结

| 场景 | 推荐 |
|:---|:---|
| 互联网 Web、快速迭代、成本敏感 | MySQL |
| 复杂分析、GIS、JSON、高扩展性需求 | PostgreSQL |
| 大型企业核心系统、预算充足 | Oracle |
| .NET 生态、微软体系 | SQL Server |

## 三、非关系型数据库横向对比

| 对比维度 | Redis | MongoDB | Elasticsearch | HBase |
|:---|:---|:---|:---|:---|
| 数据模型 | Key-Value（含丰富结构） | 文档（BSON） | 文档（JSON）+ 倒排索引 | 列族（Key-Value 宽表） |
| 存储介质 | 内存（可持久化） | 磁盘（内存映射） | 磁盘（段文件） | HDFS |
| 主要用途 | 缓存、分布式锁、计数、排行榜 | 灵活 Schema 的业务数据 | 全文检索、日志分析 | 海量数据随机读写 |
| 查询能力 | 键查询、简单结构操作 | 二级索引、聚合管道 | 全文检索、聚合分析 | RowKey 范围扫描 |
| 水平扩展 | Cluster 分片（16384 槽） | 分片（Shard）+ 副本集 | 分片（Shard）+ 副本 | Region 自动分裂 |
| 一致性 | 最终一致（可调） | 可调（读关注/写关注） | 最终一致（近实时） | 强一致（单行） |
| 事务 | 单命令原子，6.0+ 支持多命令 | 4.0+ 支持多文档事务 | 不支持 | 单行原子 |
| 典型场景 | 缓存、会话、限流、排行榜 | 内容管理、物联网、用户画像 | 搜索、日志、监控 | 日志、时序、超大规模 KV |

### Redis

- **定位**：高性能内存 KV 数据库，常用于缓存。
- **数据结构丰富**：String、List、Hash、Set、ZSet、Bitmap、HyperLogLog、GEO、Stream。
- **对比 Memcached**：Redis 支持的数据类型更丰富（Memcached 仅支持简单 KV），支持持久化与集群，还提供分布式锁等能力。
- **集群方案**：主从复制、哨兵（Sentinel）、Cluster 分片（16384 个哈希槽）。
- **持久化**：RDB（快照）+ AOF（命令追加）。
- **适用**：缓存加速、分布式锁、计数器、排行榜、限流、会话共享。

### MongoDB

- **定位**：面向文档的 NoSQL 数据库，由 C++ 编写，基于分布式文件存储。
- **数据模型**：以 BSON 文档存储，字段值可嵌套文档、数组，无需预定义 Schema。
- **主键 `_id`**：未指定则自动创建 ObjectId，结构为「4 字节时间戳 + 3 字节机器 ID + 2 字节进程 ID + 3 字节计数器」，可保证同一进程同一时刻不重复。
- **存储引擎**：WiredTiger（默认，支持文档级并发、快照、检查点、压缩、Journal 日志）、In-Memory 等。
- **宕机恢复**：类似 MySQL redo log，写数据前先顺序追加 Journal 日志，再写内存，定期刷盘；不是准实时写入，但可高吞吐。
- **集群模式**：
  - 副本集（Replica Set）：主从复制，提供冗余备份与高可用。
  - 分片（Sharding）：横向扩展，三大组件为 mongos（路由）、Config Server（配置）、Shard（分片）。
- **适用**：内容管理、物联网、用户画像、日志存储等 Schema 灵活、数据量大的场景。

### Elasticsearch

- **定位**：兼具搜索引擎与 NoSQL 数据库能力的开源系统，基于 Java/Lucene 构建。
- **核心能力**：全文搜索、结构化搜索、近实时分析。
- **名词对应**：索引（index）≈ 库/表，文档（document）≈ 行，映射（mapping）≈ Schema，类型（type，7.x 后已废弃）。
- **倒排索引**：由 Posting List、Term Dictionary、Term Index 组成，Term Index 使用 FST（有限状态转换器）压缩，内存占用小。
- **集群**：节点（Node）、集群（Cluster）、分片（Shard）、副本（Replica）。
- **选主**：7.x 之前用 Bully 算法（存在 Master 假死、脑裂问题），7.x 之后改用类 Raft 算法。
- **优化手段**：加大 filesystem cache、数据预热、冷热分离、合理设计 document、禁止深度分页（用 search_after）。
- **为什么快**：倒排索引 + 分片并行 + Filesystem Cache + 段合并机制。
- **适用**：搜索、日志分析（ELK）、监控、复杂聚合统计。

### HBase

- **定位**：基于 HDFS 的分布式列式存储数据库，支持海量数据随机读写。
- **数据模型**：Row Key、列族（Column Family）、列、Cell、TimeStamp（版本号，列可动态添加）。
- **架构组件**：Region、HMaster、RegionServer、ZooKeeper、HDFS。
- **写入流程**：数据先写 WAL → MemStore → 达到阈值后 Flush 成 HFile。
- **读取流程**：Block Cache + MemStore + HFile 合并读取。
- **Compaction**：Minor Compaction（小合并）、Major Compaction（大合并，清理删除数据）。
- **Region 管理**：Region 按连续 Key 划分，过大自动分裂，HMaster 负责负载均衡与故障恢复。
- **优势**：海量数据（PB 级）、高并发随机读写、自动分区、强一致（单行）。
- **劣势**：不支持复杂查询与 JOIN、不擅长小数据量、RowKey 设计不当易热点。
- **适用**：海量日志、时序数据、超大规模 KV 存储、需要随机读写的场景。

## 四、总结与选型建议

### 选型决策路径

1. **是否需要强事务与复杂关联查询？**
   - 是 → 关系型数据库（MySQL / PostgreSQL / Oracle / SQL Server）
   - 否 → 进入下一步

2. **核心诉求是什么？**
   - 缓存 / 高并发读写 / 分布式锁 → Redis
   - 全文检索 / 日志分析 / 聚合统计 → Elasticsearch
   - 灵活 Schema 的文档数据 → MongoDB
   - 海量数据 KV 随机读写 → HBase

3. **关系型数据库内部如何选？**
   - 成本敏感 + Web 应用 → MySQL
   - 复杂分析 / GIS / JSON / 高扩展 → PostgreSQL
   - 大型企业核心 + 预算充足 → Oracle
   - 微软技术栈 → SQL Server

### 常见组合

- **互联网业务**：MySQL（业务数据）+ Redis（缓存）+ Elasticsearch（搜索/日志）
- **数据分析平台**：PostgreSQL（数仓）+ HBase（明细存储）+ Elasticsearch（检索）
- **企业核心系统**：Oracle（交易）+ Redis（缓存）
- **.NET 企业应用**：SQL Server + Redis

> **核心原则**：没有最好的数据库，只有最适合的数据库。实际生产系统往往是多种数据库组合使用，各自发挥所长。
