**项目名称**：日志系统　**角色**：后端开发

**技术栈**：Spring Boot + MyBatis-Plus + PostgreSQL + Elasticsearch 9 + Redis + Fluent Bit

**项目介绍**：由 0 到 1 设计与开发的自研集中式日志平台，参照 ELK 架构构建「采集 → 传输 → 双存储 → 检索 → 告警 → 权限」全链路能力，为多服务集群提供集中式日志管理与主动告警。

**个人工作内容与成果**：

4. **数据权限体系**：采集准入采用多源密钥，SHA-256 加盐存库、界面可配、支持单独吊销与轮换，密钥归属用户并随日志全链路落库；数据权限由服务、主机、环境、日志类型四维授权与密钥归属通道取并集构成，用户分级管理，管理员同样受「无授权不可见」约束，杜绝越权旁路。
5. **检索与实时链路**：深分页采用 search_after 游标方案，突破 from+size 万条窗口限制；SSE 逐条实时推送，连接建立立即输出响应头，新日志秒级可见。

## 二、第一问：从「项目介绍」行出发

### 2.1 介绍下这个项目 / 整体架构（建议 1 分钟）

**背景一句话**：多套业务系统的日志分散在各机器本地文件里，排障要逐台登录机器 grep，没有跨服务的关键字检索与链路视角，日志增长没有告警，更没有按人的数据权限管控——所以从 0 到 1 自研了一套集中式日志平台。

**一条数据流讲完架构**：

```
业务日志文件
  → Fluent Bit（tail 采集 + 多行堆栈聚合 + 本地磁盘缓冲）
  → Lua 字段富化（提取 service / env / logType 等维度）
  → 采集接口（API Key 认证；入队失败回 503，采集端保缓冲重试）
  → Redis 队列削峰（接收与写入解耦）
  → 服务端消费解析（多格式解析器链 + 级别推断）
  → 双写：ES 单条流水（IK 分词、按天滚动索引）＋ PG 天级聚合
  → 对外：检索 / 统计 / SSE 实时推送 / 告警评估（邮件通知）
```

**设计思想收口三句**：采集与查询解耦（采集端无状态、查询层可独立降级）；检索与统计双轨（互为兜底）；每级失败都有明确处置（缓冲重试 / 503 / 降级标记）。

### 2.2 为什么自研，不直接用 ELK？

- 内网单机规模，ELK 全家桶（ES + Logstash + Kibana）的运维与资源成本不成比例；
- 需要按业务深度定制：**按用户的数据权限**（Kibana 租户隔离弱）、**业务化告警规则**（中文场景、邮件直连）；
- 自研只实现需要的链路，架构上参照 ELK 的分层思想（采集 agent → 缓冲 → 双存储 → 查询层）。
- **收口**：答的是成本权衡与定制深度，不是「造轮子」。

### 2.3 量级多少？（准备估算口径，别现编精确数）

- 口径：日增 XX 万条 / 峰值写入 XX 条每秒 / ES 保留 30 天 / PG 保留 60 天；
- 说出估算依据（单条平均大小 × 服务数 × 日志频率），比报一个假精确数字可信。

## 四、简历第 1 条：日志采集与双轨存储流水线

> **简历原句**：Fluent Bit 承接采集，Lua 脚本完成字段富化与多行堆栈聚合；Elasticsearch 存单条流水支撑检索，PostgreSQL 按天分表存聚合明细，以机器 IP + 日期 + 日志类型为粒度支撑统计与长期留存；聚合设置字段上限自动切分，防止单条过大拖垮回溯性能。

### 4.1 「Fluent Bit 承接采集」→ 采集端怎么工作？

- **概念**：agent 模式——tail 日志文件 → 解析（多行合并）→ 富化 → 输出到采集接口（HTTP）。
- **项目做法**：采集端只认 API Key，**不携带用户身份** → 采集与用户身份解耦（这是后面「密钥归属」权限体系的前提）。
- **追问「怎么防止把日志中心自己的日志也采了」**：必须 `Exclude_Path` 排除自身日志目录——否则日志中心自己的日志被采集，形成**正反馈循环**（自身日志量放大 5~10 倍），这是日志系统的经典自噬问题。

### 4.2 「Lua 脚本…多行堆栈聚合」→ 多行堆栈怎么聚合？★ 坑 1

- **踩坑**：最初用 Lua 自实现多行缓冲，两个致命缺陷——① 缓冲只在遇到「下一条起始行」时才输出，**每个服务的最后一批日志永久丢失**（flush 时机错误）；② 「正文含 Error/Exception 即判为续行」的模糊规则，会把带时间戳的正常 ERROR 日志**误合并**进上一条。
- **终案**：多行聚合交给 Fluent Bit 原生 `MULTILINE_PARSER`（状态机判定，自带 flush 保证），Lua 只做字段富化。
- **提炼方法论**：模糊规则不能用于流式判定；自研缓冲器必须有 flush 时机保证（超时/关闭时冲刷）。
- **追问「Lua 具体富化什么」**：提取 service、env、logType 等维度字段——这些是后面检索过滤、聚合统计、数据权限的维度基础。

### 4.3 「ES 存单条流水 / PG 按天分表存聚合明细」→ 为什么双存储？

- **答**：职责分离——ES 存单条流水（IK 分词、全文检索、按任意维度过滤），PG 存天级聚合明细（统计报表、长期留存、存储成本低）。ES 挂了统计还能用；统计需求也不会拖垮检索集群。
- **对比一句话**：ES 的粒度是**毫秒级单条**，PG 的粒度是**天级聚合行**——「能毫秒级定位某一条日志」与「只能按天看聚合块」正是两套存储的分水岭。

### 4.4 「以机器 IP + 日期 + 日志类型为粒度」→ 为什么这个粒度？

- 统计与权限的维度就是这几个，聚合键 = 主机 + 服务 + 级别 + 天；
- 明细若逐条落 PG 就是亿级，既存不起也没人逐条看月度数据——**聚合的本质是用可接受的精度损失换存储与查询成本**。

### 4.5 「聚合设置字段上限自动切分」→ 怎么切分？为什么单条大会拖垮回溯性能？

- **做法**：聚合行的预览字段设字符上限；完整原文按「100 条 / 5 万字符」分片写入明细表（超大日志被拆成多片存储）。
- **为什么单条过大有害**：ES 侧单条文档过大 → 批量写入体积膨胀、段合并变慢；查询侧回溯要传输超大字段 → 响应变慢、内存压力大。**限制单条上限是保护写入与查询两端的性能。**

## 五、简历第 2 条：可靠性设计（防日志丢失）

> **简历原句**：构建「采集端磁盘缓冲 + 应用内存队列」两级缓冲；入队失败返回 503 而非 200，使采集端依据状态码正确保留缓冲重试，杜绝网络抖动下日志静默丢失；ES 不可达时自动降级 PG 聚合兜底，检索与采集链路互不反噬。

### 5.1 「两级缓冲」→ 为什么要缓冲？两级怎么分工？

- **先答概念（削峰）**：日志产生是**脉冲式**的（发布、故障、定时任务会瞬间打高），而存储写入能力是平滑的——中间必须有缓冲层把洪峰先存下来，让下游按自己的节奏消费。
- **两级分工**：第一级 Fluent Bit 磁盘缓冲（**跨进程持久化**，应用挂了也在）；第二级应用内队列（隔离「接收接口」与「落库速率」）。本质是**用可接受的延迟换不丢数据**。
- **追问「为什么不用 Kafka」**：按量级选型——当前部署规模下，Redis 队列 + Fluent Bit 磁盘缓冲已够；Kafka 的分区与回放能力在这个量级用不上，双端改造是大工程，列入规模触发后的演进计划。**答的是判断力，不是技术不足。**

### 5.2 「入队失败返回 503 而非 200」★ 坑 2

- **答**：Fluent Bit 判定投递成功与否**只看 HTTP 状态码，不解析响应体**。若入队失败仍返回 200（哪怕 body 里写了错误码），采集端会误判投递成功、**删除本地磁盘缓冲**——缓冲期内的日志永久丢失，且**没有任何报错信号**（检索侧只是没数据，看不出是采集端丢的）。
- **真实缺陷**：入队方法吞掉了 Redis 异常（返回 void）→ 上层恒判定成功 → 返回 200。修复：异常上抛 → 返回 **503** → Fluent Bit 按失败处理、保留缓冲无限重试。
- **「静默丢失」的定义**（简历里这个词会被追问）：日志**没有写进存储、但采集端以为写成功了**——丢了却不告警、不报错，只能靠事后的数据缺口发现。这是日志系统最危险的失败模式。
- **提炼方法论**：跨进程契约要看对方的**实际判定逻辑**，而不是自己约定的语义。

### 5.3 「ES 不可达时自动降级 PG 聚合兜底」+「互不反噬」

- **怎么降级**：检索走 ES，ES 异常时自动回退 PG 聚合行映射为事件列表；粒度变粗（500 字预览而非完整原文），但**接口不中断**，响应标 `degraded=true` 让前端明确提示「当前是聚合视图」。
- **怎么保证「不反噬」**：ES 是**懒连接、非启动硬依赖**；ES 异常只记日志、不抛出——检索层故障绝不能拖跨采集主链路。**「检索挂了可以降级，采集挂了就全完了」——这是两条链路的优先级判断。**
- **追问「降级后用户体验」**：三种状态必须分开表达——**无授权 / 降级 / 空结果**，混在一起会让运维误判「系统坏了」（无授权是安全默认，不是故障）。

## 六、简历第 3 条：告警体系

> **简历原句**：设计错误率阈值、消费积压、死信、环比突增、慢接口 p95、可用性窗口等 7 类告警规则，邮件通知全流程闭环；同一故障持续期间基于指纹收敛为单条事件累计，配合静默窗口防刷屏、恢复后自动关闭，避免持续故障引发告警风暴。

### 6.1 「等 7 类告警规则」→ 逐个说清（**简历只列了 6 个名字，第 7 类是 ES 降级**）

| 规则 | 监控什么 | 判定思路 | 为什么需要这条 |
|---|---|---|---|
| 错误率阈值 | 窗口内 ERROR 占比 | ERROR 数 / 总数 > 阈值 | 最基础的健康度信号 |
| 消费积压 | Redis 队列长度 | 队列持续超阈值（消费跟不上采集） | 积压 = 日志正在堆积，再涨就触发丢弃 |
| 死信 | 多次落库失败的日志数 | 死信数 > 0 | 有日志**确实没落库**——数据缺口的确证 |
| ES 降级 | ES 不可达/异常 | 触发降级即告警 | 检索能力受损，用户看到的是聚合视图 |
| 环比突增 | 与上一周期对比 | 增长超 N 倍 | 故障早期信号（总量还没破阈值但已在异动） |
| 慢接口 p95 | 接口耗时分布 | p95 > 阈值（如 1s） | 见下 |
| 可用性窗口 | 窗口内成功率 | 成功率 < 阈值 | 服务可用性的兜底判定 |

**p95 要能讲透（概念 + 为什么不用平均值）**：
- **一句话**：把一段时间内该接口所有请求耗时从小到大排序，排在 95% 位置的值就是 p95——95% 的请求比它快，只有最慢的 5% 比它慢。「慢接口 p95 告警」= p95 超阈值就告警，含义是「最慢的那 5% 用户已经慢到不可接受」。
- **为什么不用平均值**：平均会被大量快请求稀释——100 个请求 99 个 50ms、1 个卡 10s，平均 150ms 看着健康，但真有用户等了 10 秒。p95/p99 盯的是长尾。
- **p95 还是 p99**：p99 更敏感但易被极端值牵着走、告警噪音大；p95 信号更稳，先做 p95。
- **怎么算**：日志带接口耗时字段（`durationMs`），ES `percentiles` 聚合按接口分组计算（内部 TDigest 近似算法，不必存全量原始耗时）。

**★ 坑 3（p95 这条实现里踩的）**：评估器的样本数门槛用「窗口内总条数」判定，但 ES `percentiles` 只对**带 durationMs 字段**的文档生效——没有该字段的文档不进分位计算，p95 拿到 -1 被按「百分位不可用」跳过。表现：规则参数全对、数据也有，就是不触发。**教训：门槛判定与取值计算必须使用同一样本集。**

### 6.2 「邮件通知全流程闭环」→ 通知链路怎么做？

- 流程：规则命中 → 生成/更新事件 → 通知渠道发送（SMTP 邮件）→ 写回发送结果与时间 → 事件状态推进（FIRING / RESOLVED / ACKNOWLEDGED）。
- 「闭环」的含义：**发送有结果回写**（成功/被静默/失败都落库），不是发出去就不管了——这是后面「防刷屏判定」的数据基础。

### 6.3 「基于指纹收敛为单条事件累计」→ 指纹是什么？

- **要解决的问题**：若 FIRING 期间每轮评估都新增一条事件行，持续故障一天 = 1440 条/规则，分页、导出、统计全被流水污染。
- **方案**：**指纹 = 规则 + 服务 + 级别等维度组合**；同一指纹未恢复期间**只更新** `last_fired_at`（最近触发时间）/ `hit_count`（累计命中次数），不新增行。一条事件 = 一次完整故障（FIRING → RESOLVED）。与 Alertmanager / Grafana 的事件收敛是同一心智。

### 6.4 「静默窗口防刷屏」★ 坑 4（设计推演发现的隐藏雷）

- **做法**：同一事件在 X 分钟内不重复发信。
- **隐藏雷**：事件收敛后，同一事件行的「通知状态」字段会被后续轮次**覆盖**——防刷屏若按「状态是否等于已发送」判定「窗口内发过没有」，收敛后这个字段被改成「已静默」，于是**再也查不到「发过」，防刷屏整体失效、每轮都发邮件**。必须按**通知时间**（只在发送成功时写入、单调递增、不被覆盖）判定。
- **这个坑单轮测试测不出来**（第一轮正常，第二轮才复现），是设计收敛逻辑时推演出来的——讲这个最能体现设计深度。**教训：判定状态要用单调字段，不能用会被覆盖的状态字段。**

### 6.5 「恢复后自动关闭」→ 恢复怎么判定？

- 连续 N 轮评估窗口内无命中 → 自动置为 RESOLVED 并发恢复邮件；
- 人工确认（ACKNOWLEDGED）状态不会被自动改回 FIRING——**人工判断优先于自动规则**。

## 七、简历第 4 条：数据权限体系

> **简历原句**：采集准入采用多源密钥，SHA-256 加盐存库、界面可配、支持单独吊销与轮换，密钥归属用户并随日志全链路落库；数据权限由服务、主机、环境、日志类型四维授权与密钥归属通道取并集构成，用户分级管理，管理员同样受「无授权不可见」约束，杜绝越权旁路。

### 7.0 先答概念：什么是数据权限？和功能权限的区别？

- **一句话**：功能权限管「**能不能用**这个功能/菜单」，数据权限管「**用的时候能看到哪些数据**」。两个运营都能用检索页（功能权限相同），但 A 只授权了订单服务，就搜不到支付服务的日志。
- **日志场景为什么尤其重要**：日志天然含跨系统信息（一段异常堆栈可能带着别的服务的数据细节），不做数据权限的话，任何能用检索的人等于能看全部系统的日志。

### 7.1 「多源密钥，SHA-256 加盐存库、可配、可吊销轮换」→ 为什么多源？

- **一源一钥的价值**：可**单独吊销**（某采集端泄露不影响其他）、可**审计**（最后使用时间定位泄露源）、**加机器不改代码**（界面上建源拿 key）——一个全局万能密钥这三条全做不到。
- **安全细节（面试官爱听且体现真做了）**：SHA-256 **加盐**存库（拖库也还原不出明文，防彩虹表）；`MessageDigest.isEqual` **常量时间比较**防时序攻击；**明文只在创建/轮换时返回一次**，库里只存摘要。
- **轮换怎么做**：平滑切换 = 新旧两条记录并存 → 看旧 key「最后使用时间」确认采集端已全部切走 → 再删除旧记录。

### 7.2 「密钥归属用户并随日志全链路落库」→ 归属怎么落库？怎么防伪造？

- **落库**：密钥绑定归属用户（采集源表带 owner），日志写入时把「来源 ID」作为字段一起落库（ES 数值类型，可 terms 过滤）。
- **防伪造（关键）**：来源 ID 由**服务端从 API Key 解析结果填充，绝不采信采集端自报的值**——否则采集端可以随便声明自己的归属，等于伪造权限归属。

### 7.3 「四维授权与密钥归属通道取并集」★ 坑 5 的所在

- **模型**：可见 = **四维 scope（服务 / 主机 / 环境 / 日志类型，同维 OR、跨维 AND）∪ 密钥归属通道**（我名下 key 采到的日志）。
- **为什么是并集不是交集**：两条通道是**互补**的——四维授权管「我被允许看什么维度」，归属通道管「我自己采的数据天然归我看」。做成交集会让用户什么都看不到。
- **⚠️ 陷阱（讲给面试官听的点）**：同维 OR、跨维 AND、两通道之间 OR——三种布尔组合容易写错，**把 union 误实现成 AND 就是「用户什么都搜不到」**。
- **★ 坑 5：两个真实越权缺陷（最硬的素材）**：
  - **缺陷 ①（降级路径全表泄漏）**：降级查询的过滤器**方法签名收了 env / logType 参数，方法体里没赋值**（也没有 getter）——只授权了「环境」维度的用户走降级路径时，SQL **一个条件都不加，直接拿到全表**。修复：这类用户降级时 **fail-closed 返回空**（安全默认，不是故障）。
  - **缺陷 ②（防线从未接线）**：告警评估里的防越权校验方法**实现了、但没有任何调用点**（死代码），跳过计数恒为 0——用户被收权后，规则仍照常评估别人的服务数据，**通过告警间接获知不该看的服务**。修复只补一行接线。
  - **共同教训（面试点睛）**：「**写了 ≠ 接上了**」——签名收参数没赋值、方法实现了没调用，**编译和调用处都看不出来**；两个都是「只做编译验证」时期留下的，端到端按角色实测才暴露。
  - **追问「怎么发现的」**：收官阶段主动做「遗留验证面清单」排查发现的，不是线上事故——体现验收纪律。
- **fail-closed 的设计哲学**（可单独讲）：漏改调用点的后果应该是「看不到数据（立刻发现）」，而不是「越权看到数据（长期无人察觉）」。同类做法：接收两个参数的权限校验重载，遇到配了其他维度的 scope 时**直接拒绝**而非放行。

### 7.4 「用户分级管理」→ 怎么分级？

- 管理员建 A 级，A 级建 B 级；
- 分配边界收敛：A 级只能把**自己名下 key 采的日志**分配给自己创建的 B 级——不能把没有权限的东西分出去。

### 7.5 「管理员同样受『无授权不可见』约束」→ 为什么？

- **管理权与数据权正交**：管理员是「日志中心的运维管理者」（建 key、建用户、配授权），不等于「能看所有业务日志」。这是两个定位，混为一谈就会出现「管理员默认看一切」的惯性设计。
- 要看日志必须像普通用户一样**显式授权**，且授权动作留审计。
- **安全默认**：无任何授权 = 看不到任何日志（不是放开）。

## 八、简历第 5 条：检索与实时链路

> **简历原句**：深分页采用 search_after 游标方案，突破 from+size 万条窗口限制；SSE 逐条实时推送，连接建立立即输出响应头，新日志秒级可见。

### 8.1 「search_after 游标方案」→ 原理？为什么 1 万条限制？

- `from+size`：协调节点要归并**所有分片**的 `from+size` 条结果，内存与开销随翻页深度爆炸，所以 ES 硬限 1 万条。
- `search_after`：拿**上一页末条的排序值**做游标，每次只取之后的 topN，成本与页深无关——代价是**不能跳页**。
- **场景驱动选型**：日志检索天然是「连续往下翻 + 导出」，不需要跳页，这个代价可接受。
- **追问「游标怎么保证不漏不重」**：排序需要稳定 tiebreaker——本项目用文档自身的 `id` 字段（数值），不能对 `_id` 排序（ES 直接 400）；同毫秒的多条日志若无 tiebreaker 会在页边界重复或漏读。

### 8.2 「SSE 逐条实时推送」→ 为什么不用 WebSocket？

- 单向推送（服务端 → 浏览器）场景，SSE 更轻：纯 HTTP 语义、浏览器 `EventSource` **自动重连**、无需协议升级；代价是只支持文本、单向——日志推送正好都是。
- **三个真实踩坑**：
  1. `EventSource` 不能自定义请求头 → 令牌走 `?token=` 查询参数；
  2. `onerror` **不能主动 close**——否则浏览器不再自动重连（假死另做看门狗 + 手动重连）；
  3. nginx 反代必须 `proxy_buffering off` + `gzip off` + 足够长的 `read_timeout`——**三处缺一不报错，但数据下不来**（典型的「静默失效」）。

### 8.3 「连接建立立即输出响应头」→ 为什么专门强调这句？

- **问题**：SSE 第一次写数据之前不会送出 HTTP 响应头，而浏览器的「已连接」事件必须等响应头——若挂上连接就返回，这条连接的响应头只能等**首条日志**（数据推送只在有新日志时才发、心跳又是 30 秒一次），于是「已连接」要等 5-6 秒，且**取决于日志频率**（时快时慢，表现飘忽）。
- **修法**：建连后立即发一个**注释帧**（不产生前端事件，只为 flush 响应头），必须 try/catch（客户端可能此刻已断开）。
- **实测结果**：首字节时间 2.18s → **0.009s**。
- **这一句的价值**：拿着实测数字讲一个「非功能细节」的定位与修复过程，是「真做过」的最强信号之一。

## 附录 B：八股延伸（技术栈相关的基础题）

> 面试官会从技术栈的每个词往原理追问一层。答题**先答原理、再带一句项目用法**，把八股题变成项目加分题。

### Elasticsearch（最容易被深挖）

| 八股问法 | 答案要点 |
|---|---|
| 倒排索引是什么？ | 正排：文档→词；倒排：**词→文档列表**。写入时把文本分词成 term，每个 term 指向包含它的文档 ID 及词频/位置；检索是查 term 取列表——所以关键词查日志毫秒级，而 PG 的 `like '%x%'` 是全表扫描 |
| 写入一条数据的流程？ | 写内存 buffer，同时追加 **translog**（防宕机丢失）→ **refresh**（默认 1s）把 buffer 生成新 segment、此刻才可搜索 → 周期性 **flush** 把 segment 持久化落盘并清空 translog |
| 为什么是近实时（NRT）？ | 可搜索要等 refresh，默认 1 秒——「刚采的日志搜不到」先想到这层，不是丢了 |
| from+size 为什么限制 1 万？ | 见 §8.1 |
| text 和 keyword 的区别？ | text 分词、全文检索、默认不可聚合排序；keyword 不分词、精确匹配、可聚合可排序。项目里服务名双挂：模糊检索用 text 原字段，精确过滤/聚合走 `.keyword` 子字段 |
| IK 两种分词模式？ | ik_max_word 最细切分（**索引时**用）、ik_smart 粗粒度（**查询时**用，减少误召回） |

### Redis

| 八股问法 | 答案要点 |
|---|---|
| Redis 为什么快？ | 纯内存 + 单线程命令执行（无锁竞争、无上下文切换）+ IO 多路复用（epoll）+ 高效数据结构 |
| List 底层实现？ | quicklist：双向链表串多个 listpack 小节点——兼顾插入效率与内存紧凑。项目用法：入队 + 批量消费 + 限长（超出丢弃最旧） |
| RDB 与 AOF？ | RDB 定时全量快照：文件小恢复快、可能丢最后一段；AOF 追加命令日志：丢得少、文件大恢复慢；4.0+ 混合持久化。缓冲场景可接受少量丢失 |
| 过期删除与内存淘汰？ | 过期：惰性删除（访问时查）+ 定期抽样删除；淘汰：达到 maxmemory 按 allkeys-lru / lfu 等策略淘汰 |

### Spring / Java / MyBatis

| 八股问法 | 答案要点 |
|---|---|
| Spring 事务失效场景？ | 自调用（不走代理）、非 public 方法、异常被 catch 吞掉、默认只回滚 RuntimeException。项目「ES 异常只记日志不抛」正是**有意利用**：ES 故障不能拖采集主链路回滚 |
| 嵌套事务 / 独立事务？ | 独立事务（REQUIRES_NEW）会挂起外层、新开一个。项目里批量落库**按分片独立事务**：一片失败只回滚该片，不影响其他片 |
| Spring Boot 自动配置原理？ | `@EnableAutoConfiguration` → 读自动配置类清单 → 条件注解（`@ConditionalOnClass` 等）筛选 → 用户自定义 Bean 优先 |
| 责任链模式？ | 处理器按序尝试、能处理则接手。项目解析器链：增强格式 → JSON → 多行 → 分隔符，各实现 `supports()` / `parse()`，新格式加一个解析器即可扩展 |
| MyBatis 批量插入怎么优化？ | 单条 SQL 批量 insert（而非循环单条）+ 分批提交控制事务大小；先批量预查询已存在记录再 insert/update 分流，**消除 N+1 查询** |
| `#{}` 与 `${}` 的区别？ | `#{}` 是预编译占位符（PreparedStatement 参数，防注入）；`${}` 是字符串拼接（**有注入风险**），只用于表名/排序字段这类无法参数化的位置，且必须白名单校验 |

### 网络 / HTTP

| 八股问法 | 答案要点 |
|---|---|
| SSE 的原理？ | 普通 HTTP 长连接，`Content-Type: text/event-stream`，服务端持续写 `event/data/id` 帧，浏览器 `EventSource` 自动重连。比轮询省请求；比 WebSocket 少协议升级、只单向文本 |
| 503 与「200 + body 错误码」的区别？ | 503 从 **HTTP 语义层**告诉调用方「不可用、应重试」，中间层和重试逻辑都认；200+错误码只有解析 body 的调用方才知道失败——Fluent Bit 不解析 body，回 200 会静默丢日志（坑 2 的理论根基） |
| HTTP 状态码分类？ | 2xx 成功 / 3xx 重定向 / 4xx 客户端错（**重试无用**）/ 5xx 服务端错（**可重试**）——503 属于「服务暂时不可用」，正是采集端该重试的信号 |

### PostgreSQL

| 八股问法 | 答案要点 |
|---|---|
| 聚合表为什么快？联合索引怎么建？ | 聚合后行数 = 维度基数乘积，统计在**小表** group by；联合索引遵循**最左前缀**原则，条件要从最左列开始才走索引 |
| 事务隔离级别？ | PG 默认 Read Committed（语句级快照）；项目是定时批量写 + 统计读，默认够用 |
| `SELECT` 非聚合列为什么必须出现在 `GROUP BY`？ | SQL 标准要求——否则该列返回哪一行的值不确定（本项目按周/月统计时就踩过 `SELECT` 用 `TO_CHAR`、`GROUP BY` 用 `EXTRACT` 导致的报错） |
