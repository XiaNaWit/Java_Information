## 二、Java 基础与并发

### HashMap

**要点**：数组 + 链表 + 红黑树（1.8）；默认容量 16、负载因子 0.75；扩容 **2 倍**是因为定位用 `(n-1) & hash`，容量是 2 的幂时等价于取模但更快，且扩容后元素**要么留在原位、要么移到"原位+旧容量"**，不需要重算 hash；树化阈值 8、退化阈值 6 **不对称是为了防止在边界反复转换**（抖动）；线程不安全，并发 put 可能丢数据/成环（1.7 头插）。

- 📁 你的资料：`JAVA/Java-基础/map源码解读.md`、`img/hashmap/`
- 🔗 **项目接法**：日志系统的 Redis List 队列满时 `LTRIM` 丢最旧（不是 HashMap，但同样体现"数据结构选择要匹配语义"）。

### ConcurrentHashMap

**要点**：1.7 分段锁（Segment 继承 ReentrantLock，并发度 = 段数，固定）；1.8 改为 **CAS + synchronized 锁桶头节点**，并发粒度更细、支持红黑树；`size()` 用 `baseCount + CounterCell[]` 分散计数（类似 LongAdder）避免热点。
**为什么弃用分段锁**：并发度受段数限制、内存开销大、且 1.8 的锁粒度更细后收益不再。

- 📁 `JAVA/Java-基础/Java 容器.md`

### ThreadLocal ← **你有真实素材，务必接项目**

**要点**：`ThreadLocalMap` 的 Entry key 是 `WeakReference<ThreadLocal>`；**key 被 GC 回收后 value 仍被线程强引用** → 线程池线程长期存活 → 内存泄漏。所以要 `remove()`（尤其在线程池场景）；`InheritableThreadLocal` 在线程池下**失效**（线程复用，不会重新继承）。

**🔗 项目接法（PLM 多租户）**：
> "我们多租户的租户上下文就是 `ThreadLocal`（`TenantSchemaContextHolder` 三个变量），
> **Web 线程里 `preHandle` 设置、`afterCompletion` 清理**，链路完整。
> 但**异步线程/定时任务/MQ 消费者里取不到** —— 这就是 `InheritableThreadLocal` 在线程池下失效的同一个问题。
> 我实际修过一次（异步收集日志写错了租户 schema），当时的解法是**把 schema 变成显式入参**（`buildCacheKeyWithSchema`），
> 更彻底的做法是 `TransmittableThreadLocal`。"

- 📁 `JAVA/Java-多线程/ThreadLocal.md`

### 线程池

**要点**：核心线程数 → 队列 → 最大线程数 → 拒绝策略（AbortPolicy 默认 / CallerRunsPolicy / DiscardPolicy / DiscardOldestPolicy）；`allowCoreThreadTimeOut`；无界队列（`LinkedBlockingQueue` 默认容量 `Integer.MAX_VALUE`）会导致 `maximumPoolSize` 失效、任务堆积到 OOM。

**🔗 项目接法**：日志系统的"入队失败返回 503"本质是**背压**：与其用无界队列把内存撑爆，不如**快速失败**让上游（Fluent Bit）保留缓冲重试。

- 📁 `JAVA/Java-多线程/线程池.md`、`img/Java多线程/ThreadPoolExecutor原理流程.png`

### synchronized / volatile / CAS / AQS

**要点速记**：
- `synchronized` 锁升级：无锁 → 偏向锁 → 轻量级锁（CAS 自旋）→ 重量级锁（OS 互斥量）；偏向锁 JDK 15 后**默认禁用/废弃**（撤销成本高，且现代应用竞争多）。
- `volatile`：保证可见性与有序性（内存屏障），**不保证原子性**；`i++` 仍不安全。
- CAS：`Unsafe.compareAndSwapInt` + 自旋；三大问题 = ABA（`AtomicStampedReference` 解决）、自旋开销、只能保证一个变量。
- AQS：`state` + CLH 双向队列 + `acquire/release` 模板方法；`ReentrantLock` 公平/非公平的差异在**是否检查队列前驱**。

- 📁 `JAVA/Java-多线程/锁机制.md`、`AQS.md`、`CAS.md`、`volatile.md`

## 三、Spring

### AOP 失效场景 ← **你项目里就有注解，必问**

**要点**：
1. **同类内 `this` 自调用**（不走代理）→ 注入自身 / `AopContext.currentProxy()` / 拆类；
2. 方法 `private` / `final` / `static`；
3. 注解在接口方法上但用 CGLIB 代理（或反之）；
4. 对象不是 Spring 管理的（`new` 出来的）。

**🔗 项目接法（OA 审计）**：
> "我们的 `@EditLog` 通过 `@Around("@annotation(...)")` 拦截，注解都打在 **Controller 方法**上由外部请求进入，所以不存在自调用问题。
> 但要放到 Service 内部互调就会有 —— 这是 AOP 代理模型的固有限制。"

**JDK 动态代理 vs CGLIB**：JDK 基于接口（`InvocationHandler`），CGLIB 基于继承（生成子类，不能代理 final）；Spring Boot 2.x 默认 CGLIB（`proxyTargetClass=true`）。

- 📁 `JAVA/Spring/Spring.md`、`spring常见面试题.md`

### @Transactional 失效与传播

**要点**：失效场景 = 自调用、非 public、异常被 catch 吞掉、默认只回滚 `RuntimeException`（`rollbackFor` 要显式配）、多数据源未配事务管理器。
**传播**：`REQUIRED`（默认，加入当前事务）、`REQUIRES_NEW`（挂起外层，新开事务）、`NESTED`（保存点）。

**🔗 项目接法（审计落库的事务边界 —— 这是很好的批判性思考素材）**：
> "我们审计切面自身没有 `@Transactional`，但它拦截的业务方法有，所以**审计写入落在业务事务内**；
> 而且 `recordHistory` 外面**没有 try/catch** —— 意味着**审计写失败会把业务事务一起回滚**。
> 我认为这个设计值得商榷：审计是旁路能力，通常不该影响主业务。更合理的做法是
> **`REQUIRES_NEW` 独立事务 + try/catch 隔离**，或者干脆异步化。"

### Bean 生命周期与循环依赖

**要点**：实例化 → 属性填充 → `Aware` 回调 → `BeanPostProcessor.before` → `@PostConstruct` → `afterPropertiesSet` → `BeanPostProcessor.after`（AOP 代理在这里）→ 使用 → `@PreDestroy`。
**三级缓存**解决**单例字段注入**的循环依赖：`singletonObjects`（成品）、`earlySingletonObjects`（半成品）、`singletonFactories`（ObjectFactory，用于提前暴露代理）。**构造器注入的循环依赖解决不了**（实例都创建不出来），`@Lazy` 可以。

- 📁 `JAVA/Spring/spring常见面试题.md`、`img/spring/一个bean的生命周期.png`

## 四、数据库

### SQL 慢查询排查（标准链路，背下来）

1. **先定位**：慢查询日志 / `pg_stat_statements` / `auto_explain`；
2. **看执行计划**：`EXPLAIN (ANALYZE, BUFFERS)` —— 重点看**估算行数 vs 实际行数**（差异大 = 统计信息不准或索引选择错误）、扫描方式（Seq Scan / Index Scan / Bitmap）、回表次数；
3. **检查索引**：是否命中、是否符合最左前缀、是否有隐式类型转换/函数包裹导致失效；
4. **看数据量与选择性**：区分度低的列建索引没意义；
5. **改写 SQL**：避免 `SELECT *`、深分页、子查询改 JOIN、`OR` 拆 `UNION`；
6. **更新统计信息**（`ANALYZE`）。

- 📁 `数据库/面试题/SQL优化面试题.md`、`数据库/MySQL/MySQL：优化.md`、`img/数据库/MySQL/explain.png`

### 索引与最左前缀

**要点**：B+ 树（非叶子只存键、叶子成链支持范围扫描）；联合索引 `(a,b,c)`：`a=1 AND b>2 ORDER BY c` 中 **`b` 用到范围后，`c` 无法再用索引排序**（范围列会截断后续列的索引有序性）；覆盖索引避免回表；索引失效：函数、隐式转换、前导 `%`、`OR` 混合。

- 📁 `数据库/MySQL/MySQL：索引.md`、`img/数据库/MySQL/联合索引*.png`

### PostgreSQL vs MySQL ← **你用 PG，会被问**

**要点**：
- PG 的 MVCC 把**旧版本留在表里**（配合 `xmin/xmax` 事务 ID），所以需要 **VACUUM** 回收死元组、防止事务 ID 回卷；MySQL 的旧版本在 **undo log**，由 purge 线程清理。
- PG 默认隔离级别 **Read Committed**（语句级快照）；MySQL 默认 **Repeatable Read**（快照 + 间隙锁，且用间隙锁在很大程度上解决了幻读）。
- PG 的 DDL **支持事务**（MySQL 8 之前不支持）。
- PG 的 `EXPLAIN ANALYZE` 信息比 MySQL 丰富（有 BUFFERS）。

- 📁 `数据库/PostgreSQL/PostgreSQL基础.md`、`数据库/面试题/数据库对比.md`

### 软删除 + 唯一索引冲突 ← **你有真实项目经验，这题你要主动引**

**要点**：软删除后唯一索引仍占位，重录同编码会冲突。
**解法**：① **部分唯一索引**（PostgreSQL：`CREATE UNIQUE INDEX ... WHERE delete_flag = 0`）；② 把删除时间纳入唯一键（`UNIQUE(code, deleted_at)`，软删时填当前时间）；③ 软删时改写业务键（不推荐，会污染数据）。

**🔗 项目接法（主动坦白，反而加分）**：
> "⚠️ 我们 PLM **没有处理这个问题** —— 唯一约束里不含 `delete_flag`，也没捕获 `DuplicateKeyException`。
> 我复盘时认为应该用 **PostgreSQL 的部分唯一索引**（`WHERE delete_flag = 0`）来解，这是我知道的待改进项。"

- 📁 `数据库/理论/数据库设计理论.md`

## 五、Redis

### 缓存三兄弟

| 问题 | 现象 | 方案 |
|---|---|---|
| **穿透** | 查不存在的数据，缓存和 DB 都没有 | 布隆过滤器 / 缓存空值（短 TTL）/ 参数校验 |
| **击穿** | 热点 key 过期瞬间大量请求打到 DB | 互斥锁重建（`SETNX`）/ 逻辑过期（不设 TTL，异步续） |
| **雪崩** | 大量 key 同时过期 / Redis 宕机 | TTL 加随机值 / 多级缓存 / 熔断降级 |

- 📁 `中间件/Redis/Redis：缓存.md`、`img/redis/缓存穿透.png`

### 缓存与 DB 一致性 ← **你有真实提交，必须接**

**要点**：Cache-Aside 下推荐 **先更新 DB、再删缓存**（而不是更新缓存）；为什么？删缓存更不容易产生中间态，且避免并发写导致缓存被旧值覆盖。
**延迟双删**（更新前后各删一次）能缓解但不能根治 —— 更可靠的是**订阅 binlog（Canal）异步删缓存**或**分布式锁串行化**。

**🔗 项目接法**：
> "我修过一次缓存不一致：**更新方法必须先删缓存再写缓存，否则会出现读到的旧值**（提交信息原文）。
> 本质是 **Cache-Aside 顺序问题** —— 我们最后采用的顺序是'先删缓存 → 更新 DB'，配合短 TTL 兜底。"

### 分布式锁

**要点**：`SET key value NX PX` + **唯一 value** + **Lua 脚本原子释放**（比较 value 再删，防误删别人的锁）；业务超时需**看门狗续期**；Redlock 争议（依赖时钟、性能差，多数场景单实例 + 兜底更实际）。

- 📁 `中间件/Redis/Redis：分布式锁.md`、`系统设计/分布式相关/分布式锁.md`

## 六、消息队列与实时推送

### RabbitMQ 消息不丢（三环节，标准答案）

| 环节 | 手段 |
|---|---|
| **生产者→Broker** | `publisher confirm`（异步确认）/ 事务（性能差）；失败重发 |
| **Broker 内部** | 队列 + 消息**持久化**（`durable` + `deliveryMode=2`）；集群镜像队列 / Quorum 队列 |
| **Broker→消费者** | **手动 ack**（处理成功才 ack）；失败 `nack` + 死信队列（DLX）+ 重试；消费幂等（业务唯一键去重） |

**🔗 项目接法（说实情）**：
> "OA 和 PLM 里都接了 RabbitMQ，**生产端在用**（邮件走 `rabbitTemplate.convertAndSend`）。
> ⚠️ 但**消费端在仓库里是被注释的** —— 环境上没启用完整闭环，所以我只能讲生产侧的设计。"

- 📁 `中间件/消息队列/RabbitMQ.md`、`mq常见面试题.md`

### SSE vs WebSocket ← **日志系统用 SSE，必问**

| | SSE | WebSocket |
|---|---|---|
| 方向 | 单向（服务端→客户端） | 双向 |
| 协议 | 纯 HTTP（`text/event-stream`） | 需 HTTP Upgrade 握手 |
| 重连 | 浏览器 `EventSource` **自动重连** | 需自己实现心跳与重连 |
| 数据 | 只支持文本 | 文本 + 二进制 |
| 适用 | 日志推送、进度通知 | 即时通讯、协同编辑 |

**🔗 项目接法**：日志推送是**单向 + 文本**，SSE 更轻；代价是不能双向、且**集群下需要自己做广播**（我们当前单实例，这是已知未做项）。

**SSE 实战坑（讲出来极具说服力）**：
1. `EventSource` **不能自定义请求头** → token 走 `?token=`；
2. `onerror` **不要主动 `close()`**，否则浏览器不再自动重连；
3. Nginx 必须 `proxy_buffering off` + `gzip off` + 足够长的 `read_timeout`，**三处缺一不报错但数据下不来**；
4. **首次 write 前不会送出响应头** → 建连后立即发一个**注释帧** `comment("connected")` 刷响应头（我们实测 TTFB **2.18s → 0.009s**）。

- 📁 `计算机网络/HTTP与认证/HTTP.md`

## 七、手写代码题（排除"只会用 AI"）

### LRU 缓存（最高频）

**要点**：`HashMap` + **双向链表**（`LinkedHashMap` 重写 `removeEldestEntry` 最简）；`get`/`put` 都要把节点移到头部；`O(1)`。
**并发版**：`ConcurrentHashMap` + 每桶链表 + 分段锁，或用 `Caffeine`。

- 📁 `数据结构和算法/LRU.md`、`LFU.md`

### 并发找 bug（常见送分题）

高频陷阱：静态共享 `SimpleDateFormat`（→ `DateTimeFormatter` 或 `ThreadLocal`）、并发 `HashMap.put`、双重检查锁漏 `volatile`、`i++` 当计数器、`Collections.synchronizedList` 遍历未加锁。

### 重构题（正好命中你的强项）

把 `if-else` 渠道分支重构成**策略 + 工厂**：
```java
// 前：一堆 if (channel == EMAIL) {...} else if (channel == WECHAT) {...}
// 后：
public interface NotificationSender { NotificationChannel channel(); void send(RenderedMessage m, List<ContactInfo> c); }
@Component class EmailSender implements NotificationSender { ... }
// 注册：构造注入 List<NotificationSender>，用 channel() 建 Map
```
**🔗 你项目里就是这么做的**（`NotificationServiceImpl` 注入 `List<NotificationSender>`），**可以现场手写这段并说明"新增渠道只需加一个 `@Component`，门面不改"** —— 这是最漂亮的开闭原则演示。
