## 〇、先搞清楚 2026 年大厂在考什么

大厂面经汇总后有个明确结论：**题库没变，问法全变了**。同一道题，答法分两种命运：

| | 回答 A（背答案型） | 回答 B（工程判断型） |
|---|---|---|
| 问"线程池参数怎么设" | "corePoolSize 核心线程数、maximumPoolSize 最大线程数……CPU 密集型设为核数+1，IO 密集型设为 2 倍" | "参数本质是在权衡**响应速度、吞吐量、资源消耗**。我是图片处理场景（CPU 密集），核数设为 8、有界队列 1000 防 OOM、最大 16、拒绝策略用 CallerRunsPolicy 做**反压**。如果延迟敏感，我会把核心数拉满配 SynchronousQueue。另外我会监控活跃线程数和队列长度，持续增长说明要扩容。" |

**面试官现在考三个维度**：

1. **源码理解度** —— 不是背流程，而是"关键路径上的关键设计"（比如 ConcurrentHashMap 扩容时其他线程怎么帮忙迁移）
2. **线上问题定位能力** —— "CPU 飙高你怎么查""MySQL 死锁日志能不能还原出两个事务的执行顺序"
3. **设计取舍能力** —— "如果 QPS 涨十倍你的方案怎么变"，考察你说清 **trade-off**

> **一句话**：每个答案都要有"**是什么 → 为什么这么做 → 换别的方案会怎样**"三段，第三段才是分水岭。

## 一、系统设计答题框架（任何题都能套）

### 七步法（背下来）

| 步骤 | 要说什么 | 例（秒杀） |
|---|---|---|
| 1. 澄清需求 | 用户是谁、核心功能、**哪些不做** | 只做下单链路，不做商品管理后台 |
| 2. 确认指标 | 峰值 QPS、数据量、延迟、一致性 | 峰值 5 万 QPS，允许最终一致 |
| 3. 设计核心模型 | 实体、状态机、唯一键、索引 | 订单表、库存表、状态机 |
| 4. 画主链路 | 请求从入口到存储怎么走 | 网关 → 限流 → Redis 预扣 → MQ → 落库 |
| 5. 处理关键问题 | 高并发、热点、幂等、一致性 | 防超卖、防重复下单、失败回补 |
| 6. 说明扩展方式 | 到哪一步瓶颈、怎么扩 | Redis 分片、库存服务独立 |
| 7. 补充工程保障 | 监控、压测、灰度、回滚 | 库存水位、队列深度、P99 |

### 容量估算（必考，别算精确值，要算数量级）

- 平均 QPS = 日请求量 ÷ 86400
- 峰值 QPS = 平均 × 峰值系数（一般 3~5，大促更高）
- 日增存储 = 日新增条数 × 单条大小
- 总存储 = 日增 × 保留天数 ×（索引 + 副本 + 日志开销，通常 ×2~3）

> 例：日 1 亿请求 → 平均 ≈ 1157 QPS → 峰值按 5 倍 ≈ 6000 QPS。
> **主动给假设**："先按读多写少、峰值 5000 QPS、允许秒级最终一致来设计"——这比等面试官追问强得多。

### 回答检查清单（说完前自查）

- [ ] 说清了核心功能和**不做**的功能
- [ ] 说了用户量/峰值 QPS/数据量
- [ ] 讲清核心读写链路和状态机
- [ ] 处理了并发冲突、重复请求、失败重试
- [ ] 识别了单点、热点、依赖故障
- [ ] 说了哪些地方强一致、哪些允许最终一致
- [ ] 给了监控/压测/灰度/回滚方案

## 二、场景设计题（10 道高频）

### 1. ⭐ 秒杀系统（库存扣减怎么防超卖）

**考点**：高并发下的原子性、Redis 与 DB 的一致性、失败补偿。

**答案框架**：

```
① 活动预热：库存、限购规则提前加载到 Redis
② 入口过滤：验证码 / 动态路径 / 网关限流，把无效请求挡在外面
③ 库存预扣：Redis Lua 原子扣减（或 DB 条件更新）
④ 异步下单：预扣成功写 MQ，消费者创建订单（削峰）
⑤ 幂等：用户ID + 活动ID 唯一约束，防重复下单
⑥ 补偿：订单创建失败/超时未支付 → 按状态机回补库存
```

**关键 SQL**（面试官爱看）：
```sql
UPDATE sku_stock SET available = available - 1
WHERE sku_id = ? AND available > 0;
-- 受影响行数 = 1 才算扣减成功
```

**追问链**：
- **"Redis 扣了但消息没发出去怎么办？"** → 用 Redis Stream / 事务消息 / 本地消息表，保证"扣减"和"发消息"的原子性；或者接受最终一致，用库存流水对账补。
- **"Redis 挂了怎么办？"** → 降级到 DB 条件更新（`available > 0` 保证不超卖，但 QPS 会掉）；或者提前把库存分桶（一个 SKU 拆 N 份）降低单点压力。
- **"超卖了吗？"** → Redis 单线程 + Lua 保证原子性不会超卖；DB 条件更新也不会。真正的风险是**回补时重复加**。

### 2. ⭐ 短链系统

**考点**：短码生成、唯一性、跳转性能、防刷。

**答案框架**：
- **短码生成**：全局 ID 转 Base62（推荐，无碰撞）；或用长 URL 哈希（要处理碰撞）
- **数据模型**：短码唯一索引 + 长 URL + 创建者 + 有效期
- **读取链路**：热点短码进缓存；未命中查 DB，**要防随机短码打穿**（布隆过滤器/限流）
- **跳转码**：`301` 会被浏览器永久缓存（统计不了）；`302` 便于服务端统计和控制 → **选 302**
- **安全**：创建频率限制、恶意链接检测、封禁与审计

**追问**："同一个长 URL 要返回同一个短码吗？" → 要的话得加去重映射表，并处理 URL 规范化（协议、参数顺序、大小写）。

### 3. 排行榜（实时 + 上亿用户）

**考点**：Redis ZSet 的用法、分数相同时怎么排、历史榜单。

**答案框架**：
- `ZADD` 更新分数、`ZREVRANGE` 取 Top N
- **同分排序**：用"更新时间"或唯一 ID 做二级排序（否则顺序不稳定）
- **分层**：日榜/周榜/赛季榜分 Key，避免单个 Key 无限增长
- **历史榜单**：结算时生成快照归档
- **超大榜单**：分片（按用户区间），查询全局 Top N 时各分片取候选再归并
- **权威数据**：分数变更的流水要落库，Redis 挂了能从 DB/事件日志重建

**追问**："Redis 挂了榜单怎么办？" → 降级返回快照/上次结算结果；恢复后从流水重建。

### 4. ⭐ 接口幂等（几乎所有写接口都会问）

**考点**：重复请求、重试、MQ 重复消费。

**六种方案**（按场景选）：
1. **幂等键**：客户端生成唯一请求号，服务端记录处理结果
2. **唯一索引**：订单号、支付流水号建唯一约束（最简单可靠）
3. **状态机**：只允许合法流转（待支付 → 已支付，不能反向）
4. **条件更新**：SQL 带旧状态/版本号
5. **去重记录**：消费消息前查业务动作是否已完成
6. **分布式锁**：同一业务键串行化（注意锁的粒度）

**关键补充**（很多人漏）：幂等记录要有 `PROCESSING / SUCCESS / FAILED` 三态 + 过期时间，处理"卡在处理中"的情况。

### 5. ⭐ 缓存与数据库一致性

**考点**：Cache Aside、延迟双删的局限、什么时候能接受不一致。

**标准答案**：
- **读**：先查缓存，未命中查 DB 再回填
- **写**：**先更新 DB，再删缓存**（不是更新缓存）
- **为什么删而不是更新**：并发写时"更新缓存"可能被旧值覆盖；删除更安全

**追问"还有短暂不一致怎么办"**：
- TTL 兜底（错误数据不会长期存在）
- 热点 Key 回源用互斥/请求合并
- **binlog/CDC 异步删缓存**（Canal）
- 缓存值带版本号，拒绝旧版本覆盖
- **强一致读直接走 DB**

**"延迟双删靠谱吗"** → 不靠谱：延迟时间拍不准、第二次删除也可能失败，**不能当严格一致性保证**。

> 🔗 **你的项目接法**：你实际修过"更新方法必须先删缓存再写库"的 bug —— 讲这个，比背理论强。

### 6. 订单超时自动取消

**考点**：延时任务方案对比。

| 方案 | 优点 | 问题 |
|---|---|---|
| 定时扫表 | 简单、易补偿 | 时效性取决于扫描周期 |
| Redis ZSet | 按到期时间取任务 | 要处理持久化、故障恢复、并发领取 |
| **MQ 延时消息** | 链路清晰、规模好 | 依赖 MQ 的延时能力 |
| 调度平台（XXL-JOB） | 管理/重试/监控完善 | 建设成本 |

**关键**：取消时必须**检查状态**：
```sql
UPDATE orders SET status='CANCELLED'
WHERE id=? AND status='PENDING_PAYMENT' AND expire_at <= NOW();
```
已支付的订单，超时消息要**直接忽略**。取消成功后再释放库存/优惠券，每一步都要幂等。

> 🔗 **你的项目接法**：你写过 `TenantExpireHandler`（租户过期监控定时任务）—— 这就是"定时扫描"方案的真实实践。

### 7. 站内消息与推送系统

**考点**：在线/离线、未读数、重复投递。

**答框架**：
```
业务事件 → MQ → 消息服务按模板生成 → 写收件箱
在线：WebSocket / SSE 实时推
离线：下次上线拉取
其他通道：App 推送 / 短信 / 邮件（各自重试、频控、退订）
已读状态：按用户+消息分类维护
```

**关键问题**：
- 同一事件重复投递 → 消息生成要**幂等**
- 广播消息**不能**给每个用户插一条记录 → 存一份公告 + 按用户记阅读状态
- 未读数更新失败 → 能从消息记录**重算/校准**
- WebSocket 断线 ≠ 消息丢失 → 重连后按**游标/最后消息 ID 补拉**

> 🔗 **你的项目接法**：你做过的"外观+策略模式通知中心"就是这个系统的核心；而且你用 **SSE** 做过实时推送 —— 这题你有真实素材。

### 8. 热 Key 问题

**考点**：发现 + 治理。

- **发现**：监控、采样、`--hotkeys`、业务指标确认（别猜）
- **治理**：
  - 进程内短时本地缓存
  - 同 Key 并发回源**请求合并**（只放一个查）
  - 只读热点**复制多副本**，按随机/哈希分散读
  - 大对象拆分
  - 提前预热
  - 热点接口单独限流隔离

**代价**：本地缓存和多副本会增加更新难度；强一致的场景别长期用多级缓存。

### 9. ⭐ 流量突然增加 10 倍怎么办

**口诀：先保命，再定位。**

1. **入口限流**（按接口/用户/租户/优先级）
2. **服务降级**（关推荐、统计、非核心查询）
3. **削峰排队**（进 MQ，消费端按能力消费）
4. **扩容实例**（但先确认 DB/缓存/下游扛不扛得住）
5. **处理热点**（预热、合并回源、本地缓存）
6. **持续观察**（限流量、队列深度、P99、连接数）

**关键判断**：**自动扩容有延迟，不能当突发流量的唯一手段**；扩容应用可能把压力全打到 DB，导致 DB 先挂。

### 10. 大文件上传

**考点**：分片、断点续传、秒传。

- 申请上传任务 → 拿 uploadId + 分片大小 + 凭证
- 并发上传分片 → 服务端记录已完成分片
- 失败只重传缺失分片
- 全部分片完成 → 校验分片列表/大小/摘要 → 合并
- 元数据落库 → 异步做病毒扫描/转码

**追问"秒传"** → 文件哈希去重，但**必须校验用户是否有权引用该文件**（不能仅凭哈希就返回别人的资源）。

## 三、线上排查题（大厂越来越爱问）

### 1. ⭐ CPU 飙高怎么排查

```
① top 找到高 CPU 进程
② top -Hp <pid> 找到高 CPU 线程
③ printf '%x' <tid> 转十六进制
④ jstack <pid> | grep -A 20 <hex> 找到线程栈
   （或直接用 arthas: thread -n 3）
⑤ 看是业务死循环 / 频繁 GC / 正则回溯 / 锁竞争
```

**如果是 GC**：`jstat -gcutil <pid> 1000` 看 GC 频率和耗时；拿 GC 日志分析是 Young GC 频繁还是 Full GC。

### 2. 内存泄漏 / OOM 排查

```
① jmap -histo:live <pid> | head 看对象占用排行
② jmap -dump:format=b,file=heap.hprof <pid> 导出堆
③ MAT / JProfiler 分析：找 GC Roots 引用链，定位谁在持有
常见元凶：静态集合、ThreadLocal 没 remove、连接/流没关、缓存没上限
```

### 3. ⭐ MySQL 有索引却不走

**按这个顺序答**（面试官要"具体哪几种"）：

1. **隐式类型转换**：字段是 varchar，传了数字（或反之）
2. **函数/表达式包裹字段**：`WHERE DATE(create_time) = ...`
3. **前导模糊**：`LIKE '%xx'`
4. **OR 混合**：一侧无索引，整体走全表
5. **联合索引不满足最左前缀**
6. **范围查询后的列失效**：`a=1 AND b>2 ORDER BY c` 中 `c` 用不上排序
7. **数据量小 / 选择性低**：优化器判断全表更快
8. **统计信息过期**：`ANALYZE TABLE`
9. **索引列参与计算 / 类型不一致**

**加分**：拿 `EXPLAIN` 的 `rows`（估算）vs 实际对比，说明"估算偏差会导致优化器选错索引"。

### 4. Redis 变慢怎么查

```
① 先排除网络/客户端：ping 延迟、连接数、客户端超时
② redis-cli --latency / --intrinsic-latency 看本机延迟
③ slowlog get 看慢命令
④ 大 key 扫描：redis-cli --bigkeys / MEMORY USAGE
⑤ 检查是否用了 O(N) 命令：KEYS *、HGETALL 大 hash、SMEMBERS 大 set
⑥ 是否发生 RDB fork / AOF rewrite 阻塞
⑦ 是否主从同步延迟 / 集群迁移
```

**典型结论**：大 key（某 hash 200 万字段）→ 拆分；`KEYS *` → 改 `SCAN`。

### 5. 线程池打满 / 请求堆积

- 看队列长度、活跃线程数、拒绝次数（ThreadPoolExecutor 的 getter 或 Micrometer）
- 定位是**下游慢**（DB/HTTP 超时）还是**任务本身慢**
- 处理：加超时、隔离线程池、加限流、改异步
- **关键**：别用无界队列（会 OOM 且掩盖问题），用有界队列 + 拒绝策略做**反压**

## 四、深挖式基础题（针对你的技术栈）

### 1. HashMap 并发问题 / ConcurrentHashMap

**问法**："HashMap 在并发下有什么问题？ConcurrentHashMap 怎么解决的？1.7 和 1.8 区别？size() 准确吗？"

**答**：
- HashMap 并发 put 会丢数据、1.7 扩容头插还会成环（1.8 改尾插）
- ConcurrentHashMap 1.7 分段锁（Segment 继承 ReentrantLock，并发度=段数，固定）；1.8 改为 **CAS + synchronized 锁桶头节点**，锁粒度更细，支持红黑树
- **为什么弃用分段锁**：并发度受段数限制、内存开销大，1.8 的锁粒度已经更细
- **size()**：1.8 用 `baseCount + CounterCell[]` 分散计数（类似 LongAdder），并发下**不保证精确**，是近似值 —— 这点很多人不知道
- **扩容协助**：1.8 的 `helpTransfer`，其他线程发现正在扩容会帮忙迁移

### 2. ⭐ 线程池参数怎么定（工程判断型）

用"业务场景 → 参数选择 → 监控闭环"三段答：

- CPU 密集（图片处理）：核心 = 核数，队列有界（1000），最大 = 2×核数，拒绝 `CallerRunsPolicy`（反压）
- IO 密集（RPC/DB 调用）：可以设大（2×核数 ~ 更高），但更关键的是**加超时**
- 延迟敏感：核心拉满 + `SynchronousQueue`（立即执行或拒绝）
- 监控：活跃线程数、队列长度、拒绝次数 —— 队列持续增长 = 处理能力不足

### 3. ES 深分页（**你的强项，必问**）

**问法**："ES 深分页为什么慢？`from+size` 为什么限制 1 万？`search_after` 怎么解决？"

**答**：
- `from+size` 需要协调节点归并**所有分片**的前 `from+size` 条，内存和耗时随页深暴涨 → 硬限 1 万
- `search_after` 用上一页末条的排序值做游标，每次只取之后的 topN，**成本与页深无关**，代价是**不能跳页**
- **前提**：必须**稳定唯一排序**（否则同值会重复/漏读）→ 用文档自身 `id` 做 tiebreaker
- **不能对 `_id` 排序**（直接 400）

> 🔗 这是你日志系统的真实实现，讲细节碾压大部分候选人。

### 4. 分布式锁

**问法**："怎么实现？有什么坑？"

**答**：
- `SET key value NX PX`（原子加锁 + 过期）
- **value 用唯一值**，释放时 **Lua 脚本比较 value 再删**（防误删别人的锁）
- 业务超时 → **看门狗续期**
- Redlock 争议：依赖时钟、性能差；单实例 + 本地兜底通常够用
- **锁的粒度**很重要（按业务键，不要全局锁）

### 5. 事务与锁

- `@Transactional` 失效场景（自调用、非 public、异常被吞、默认只回滚 RuntimeException）
- **MySQL 间隙锁**：RR 隔离级别下防止幻读，但会死锁 → 讲一个死锁场景
- **PG 的 MVCC 与 MySQL 的区别**（你用 PG，要能对比）：PG 旧版本留表里需要 VACUUM；MySQL 旧版本在 undo log

## 五、结合你项目的"定制场景题"（面试官必问）

> 这些是**只有你的项目才会被问到的**，也是你拉开差距的地方。

### 1. 多租户：租户数从几十涨到几千怎么办？
- 先遇瓶颈：**连接数**、**PG catalog/planner 开销**、DDL 成本
- 演进：大租户独立库 + 小租户共享 schema 分层
- 更远：租户维度下沉到分库分表中间件

### 2. 多租户：跨租户统计报表怎么做？
- 不要遍历所有租户 schema（成本随租户数线性增长）
- 走**平台 schema 的汇总**，或异步 ETL 到分析库

### 3. 日志系统：10 万条/秒怎么扛？
- 采集端：Fluent Bit 多实例 + 磁盘缓冲
- 传输：削峰队列（Redis → MQ）
- 存储：ES 批量写入 + 按天索引 + ILM 冷热分层
- 落库：批量 + 分片事务
- 先崩的通常不是 ES，而是**接收端的队列和 DB 写入**

### 4. 日志系统：ES 集群整个挂 30 分钟能扛住吗？
- 短期：PG 降级兜底 + 客户端缓冲重试
- 关键："**日志不能丢**"是底线 → 采集端磁盘缓冲 + 服务端队列
- 恢复后：把缓冲的日志重放回 ES，PG 数据可回灌

### 5. 日志系统：SaaS 化对外卖，怎么设计？
- 多租户存储成本分摊（按量计费）
- 查询隔离（限流、超时、资源配额）
- 写入限流（每租户配额）
- 数据保留策略与归档

### 6. 审计：高并发下记录每条变更，性能怎么保证？
- 异步化 + 独立线程池（避免拖慢主业务）
- 批量落库
- 独立事务（审计失败不影响业务）
- 采样（非核心字段可降级）
