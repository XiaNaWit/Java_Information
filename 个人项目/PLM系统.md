### 1 分钟版（加一个取舍）

> "……其中我投入最多的是**多租户架构**。这个平台是 SaaS 化的，一个实例要服务多个租户，最开始用的是**行级隔离**（每张表加 `tenant_id`，靠 MyBatis 拦截器自动补条件）；后来整体演进到 **Schema 级隔离**——每个租户一套独立 schema。

> 迁移的原因主要是**风险面**：行级隔离下任何一条漏加条件的 SQL 都会导致**越权**；而 Schema 是物理隔离，漏写条件最多是查不到，风险小得多。"

## 三、多租户架构（**最强模块，占面试一半时间**）

### 3.1 一分钟讲清（背熟这段）

> "我们的多租户做了两代。
>
> 第一代是**行级隔离**：表里加 `tenant_id`，用 MyBatis-Plus 的 `TenantLineInnerInterceptor` + 自定义 `TenantLineHandler` 自动给 SQL 补租户条件，维护了 30 多张不参与隔离的表（菜单、字典、类型这些），超管还有差异化语义——**查询放开、写入补租户**。
>
> 后来整体迁移到 **Schema 级隔离**：按租户建独立 PostgreSQL schema。**关键实现不是切 `search_path`**，而是在 MyBatis 的 `StatementHandler.beforePrepare` 阶段做 **SQL 表名重写** —— 用 JSqlParser 解析 SQL，递归找到所有物理表，把表名改写成 `租户Schema.表名`，再反射写回 `BoundSql`。
>
> 租户上下文放在 `ThreadLocal`（平台 schema / 模板 schema / 租户 schema 三级优先级），Web 请求进来时由 `HandlerInterceptor` 根据登录用户的 `tenantId` 查出 schema 名设置进去，请求结束时清理。"

**对应代码**（面试官要证据时可以说）：
- `SchemaTableNameInnerInterceptor`（468 行，JSqlParser）
- `TenantSchemaContextHolder`（ThreadLocal 三级优先级）
- `TenantSchemaInterceptor`（Web 层设置 / 清理）

### 3.2 「为什么不用 `search_path`？」← **全篇最值钱的一击**

> "`search_path` 是**连接级/会话级**状态。连接池下连接会被反复复用——如果某个连接设了租户 A 的 `search_path`、归还时没重置干净，下一个请求复用这条连接就会读到租户 A 的数据。
>
> 这种 bug 最可怕的是：**不报错、不可复现、只在特定并发和连接复用顺序下出现**，排查成本极高。
>
> 所以我们的做法是让**租户信息随 SQL 走，而不是随连接走**：每条 SQL 自带 schema 限定符，连接本身不携带任何租户状态，归还池时天然干净。URL 里的 `currentSchema` 只是最后兜底。"

**如果追问"那用 `search_path` 你打算怎么解决？"**
> "两条路：一是拿到连接后 `SET LOCAL search_path`，让它跟随事务生命周期，事务结束自动失效；二是用 `AbstractRoutingDataSource` 按租户分组连接池，物理上不复用。
> ⚠️ **说明：这两种在我们项目里没有实现，属于我的推演。**"

> 💡 绝大多数候选人只会说"我们用了多租户"，说不出"为什么不用另一种方案、另一种方案的坑在哪"。**主动指出会话级状态的坑，是把"做过"升级为"想清楚了"。**

### 3.3 高频问题（逐个准备）

**Q1. 表名重写具体怎么实现的？**
> "`beforePrepare` 里拿到 `BoundSql` 的 SQL，用 JSqlParser 的 `parseStatements` 解析（支持多语句），按语句类型分派：`Select` / `Update` / `Delete` / `Insert` / `Replace`。
> 难点在**递归**：子查询可能出现在 `WHERE` 的 `IN`/`EXISTS`、`SELECT` 列表的标量子查询、`JOIN ON`、`HAVING`、`ORDER BY`，甚至 `CASE WHEN` 和函数参数里——我写了一个递归遍历表达式树的方法覆盖这些。
> 最后通过**反射**改 `BoundSql.sql`，因为它是 final 且没有 setter。"

**Q2. 怎么保证不误改（把别名当表名改了）？**
> "三层防护：① **CTE 别名收集**（`WITH x AS (...)` 的 `x` 跳过）；② **系统表跳过**（`pg_*`、`information_schema.*`）；③ **启发式跳过**（表名不含点、且不以 `rda_`/`sys_` 开头，判定"可能不是物理表"）。
> ⚠️ 但第 ③ 条是启发式——**新增一张不按命名规范建的表就不会被加前缀**，规范的强制性成了隔离正确性的前提。这是设计上的隐患。"

**Q3. 平台表、模板表怎么处理？**
> "`ThreadLocal` 里三个标记做优先级解析：① `USE_PLATFORM` → 平台 schema（系统表、租户元数据）；② `USE_TEMPLATE` → 模板 schema（建租户时拷表结构）；③ 当前租户 schema；④ 都没有 → 兜底回平台 schema（如系统初始化）。"

**Q4. 解析失败怎么办？** ← **诚实回答，是加分点**
> "**这是我复盘时认为最需要改进的地方**：任何 JSqlParser 异常都被 catch 住，只 `log.warn`，然后**用原始 SQL 继续执行**。
> 原始 SQL 没有 schema 前缀，会落到连接默认的 schema —— 也就是说**一条解析不了的 SQL，可能跨租户读到数据，而且不报错**。
> 我修过一次同类问题（批量插入 SQL 解析失败、异步写日志没进对应租户 schema）。**正确的做法应该是解析失败就 fail-fast 抛异常**，让问题立刻暴露。"

**Q5. 异步线程、定时任务、MQ 消费者里租户上下文还在吗？**
> "**不在**，这是 `ThreadLocal` 的固有限制。我们是纯 `ThreadLocal`，**没有** `TaskDecorator`、没有 `TransmittableThreadLocal`，线程池也没设装饰器。
> 所以 `@Async`、XXL-JOB handler 里取到的 schema 是 `null`，会走兜底落到平台 schema。
> **我实际修过这个 bug**（异步收集日志写不进对应租户 schema）。当时的解法是**逐调用点显式传 schema**：缓存统一用带 schema 参数的重载，DB 操作由调用方在 `finally` 里手工 set/clear。
> 我很清楚这不是通用解法，是**打补丁**。更彻底的做法是 `TransmittableThreadLocal`，或者把租户上下文作为显式参数贯穿。"

**Q6. 连接池用的什么？**
> "Druid（不是 HikariCP，项目沿用了若依的技术选型）。"

**Q7. 那你们有没有"会话级状态被连接池复用"的风险？** ← **升维打击题**
> "有，但**载体不是 `search_path`**，而是租户初始化时用的 `SET session_replication_role = 'replica'`——建租户时要关外键约束做 `INSERT INTO ... SELECT` 拷模板表数据，这是个**会话级 GUC**。
> 风险在于：如果事务中途进入 aborted 状态，`catch` 里想恢复成 `origin` 的语句同样会失败、而且被 `ignore` 掉了——那么这个 GUC 就**残留在连接上**，归还池后被其他请求复用，会影响它们的外键约束行为。
> 这是我复盘时回溯出来的。**用 SQL 重写只是把"租户"这个维度避开了，不代表这套系统没有会话状态风险。**"

**Q8. 行级隔离怎么做的？**（注意：行级代码在 OA 库的分支上）
> "行级是**我在 OA 库先落地的**，用的是 MyBatis-Plus 官方 `TenantLineInnerInterceptor` + 自定义 `TenantLineHandler`：
> - `getTenantId()` 从登录用户取 `tenantId`；
> - `ignoreTable()` 维护 30+ 张免隔离表；
> - **超管差异化语义**：开启多租户时超管**查询不加租户条件**（能看全部），但**插入必须补租户 ID**，且优先从业务上下文解析目标租户；
> - **启动阶段整体跳过**。
>
> 后来在 PLM 这边**整体演进到 Schema 隔离**，行级代码已清除。"

**Q9. 行级隔离遇到过什么问题？**（有真实素材）
> "最大的坑是 **MyBatis-Plus 的 `TenantLineInnerInterceptor` 会重复追加 `tenant_id`**：当手写 INSERT 的列里已经带了 `tenant_id` 时，插件会再追加一次，导致列数和值数不匹配、SQL 直接报错。
> 我的解法是写一个 `DuplicateTenantIdInterceptor`：用**正则**匹配列列表末尾的 `, tenant_id)` 和值列表末尾的 `, '值')` 删掉多余的，支持多条 INSERT。
> ⚠️ **但我很清楚这个方案脆弱**——靠正则匹配 SQL 文本，格式化差异、值里含逗号都可能失配。更稳的做法是升级 MyBatis-Plus 或从 SQL 生成源头修。我 2026-07 重构过它让它适应更多情况，但**本质还是在补框架的洞**。"

**Q10. 缓存怎么做的多租户隔离？一致性怎么保证？**
> "key 前缀带 schema：`schema::业务常量`。租户维度来自 `ThreadLocal`。
> 异步/批量场景取不到上下文，所以我加了**带 schema 参数的 key 重载**，把租户维度变成显式入参，用在缓存预热（遍历所有租户）、精准清理、全库清理三个场景。
> 一致性上我修过一次：**更新方法必须先删缓存再写库**，否则会出现读到旧值的情况。"

**Q11. 租户开通、套餐切换的并发与事务？**
> "`initTenantSchema` 和 `changeTenantMenuByPackage` 都加了 `@Transactional(rollbackFor = Exception.class)`，串行执行"生成租户编号 → 建租户记录 → 初始化 schema"。
> 幂等做了四件事：schema 存在性预检、`CREATE SCHEMA IF NOT EXISTS`、菜单导入前去重、序列 `CREATE SEQUENCE IF NOT EXISTS` + `setval` 对齐模板的 `last_value`（防新租户主键冲突）。
> ⚠️ **已知缺陷**：预检和 `CREATE TABLE (LIKE ... INCLUDING ALL)` 之间有**检查-执行竞态**（后者还没有 `IF NOT EXISTS`），开通路径**没有分布式锁**；拷模板表也没有分批，是一次性全表拷贝。"

### 3.4 避坑提示

- 🚫 不要说"用 `search_path` 做隔离"——代码里**没有任何** `search_path`/`SET SCHEMA`
- 🚫 不要说"两套方案并行运行"——行级已被清除，是**演进关系**
- 🚫 不要说你用过 `TenantLineInnerInterceptor`（在 PLM 里）——它在 **OA 库**
- ✅ 主动交出 Q4（解析失败静默降级）和 Q7（`session_replication_role` 残留）这两个真实风险，**比背答案更能体现深度**

## 四、通用软删除 + XXL-JOB

### 高频问题

**Q1. 为什么 `@TableLogic` 不够用？**
> "`@TableLogic` 只对 MyBatis-Plus `BaseMapper` 的标准 CRUD 生效，但项目里**大量使用动态 Mapper + 手写 XML + 原生 SQL**（比如租户模块全走 `dynamicMapper.selectDataList`），`@TableLogic` 完全管不到。
> 所以我**另加了一个自研 SQL 拦截器**，在 `beforePrepare` 阶段给 `SELECT` 注入 `delete_flag` 条件。"

**Q2. 这个方案的边界在哪？**（诚实交代）
> "① **只处理 SELECT**，INSERT/UPDATE/DELETE 不注入；② 表名是**启发式白名单**（只认 `rda_`/`sys_` 前缀）；③ WBS 模块用的是 `is_delete` 字段，不在覆盖范围内——这是字段命名不统一留下的口子。"

**Q3. 子查询场景怎么处理的？**（你简历里写了）
> "拦截器解析 SQL 时要**递归处理子查询**——`WHERE` 里的 `IN`/`EXISTS`、`JOIN ON` 条件这些。如果只处理主查询，子查询里的表就会漏掉删除标识，导致已删除的数据被关联出来。我修过这个 bug。"

**Q4. 软删后重新录入同一个编码，唯一索引冲突怎么办？**（诚实）
> "⚠️ **这一点我们没处理**：唯一约束里不含 `delete_flag`，代码里也没捕获 `DuplicateKeyException`。
> 正确做法是用 PostgreSQL 的**部分唯一索引**（`WHERE delete_flag = 0`），或把删除时间纳入唯一键。"

**Q5. XXL-JOB 物理清理怎么做的？**
> "设计是遍历所有可用租户 schema，查 `information_schema.columns` 找出带 `delete_flag` 的表，逐表执行 `DELETE WHERE delete_flag = 1`。
> ⚠️ **目前代码处于注释状态**——因为**公司层面停用了 XXL-JOB 组件**，测试环境把注册与任务代码注释掉了，**恢复只需放开配置**。
> 注释版实现本身也不完善：**没有分批**（整表 DELETE）、**没有幂等设计**、没有删除审计，这些是我如果要正式上线会补的。"

### 避坑提示

## 五、通知中心重构

### 高频问题

**Q1. 为什么要重构？原来什么样？**
> "原来发送逻辑散在 `EmailUtil` 和 `WeChatUtils` 里，各自持有 `RabbitTemplate`，每加一个渠道都要改调用方。重构后收敛成四层：

**Q2. 新增一个渠道要改几个类？**（开闭原则）

**Q5. 发送失败了怎么办？有重试吗？**

## 六、SSO 单点登录（⚠️ **口径必须改，最危险的一条**）

### 先说事实

| 简历写的 | 代码事实 |
|---|---|
| "基于 **OAuth2.0 授权码模式 + OIDC 协议**接入统一认证中心" | `oauth2Login()` 与 `client`/`provider` 配置**全部被注释**；实际生效的是**自研 HTTP token 代理**（`/loginSso` 转发到认证中心的 `ssoLogin`）；代码解析的是 **access_token 的 payload**（人工 Base64 解码），**不是 `id_token`**；无签名/`iss`/`aud` 校验、无 `nonce` |

### 三个可选口径（选一个，别硬撑）

**A（推荐）**：`完成统一认证中心接入与用户自动映射、权限加载，内部会话由 JWT + Redis 维护`

**B（保留关键词）**：`参与 OAuth2 / OIDC 接入方案设计与统一认证中心接入` —— 注意用"**设计**"，别写"集成/打通"

**C（被问到时如实说）**：
> "OAuth2/OIDC 的**客户端接入方案我们设计并搭了骨架**，但当前环境实际走的是**自研 HTTP 转发**：前端跳认证中心，回调后我们拿凭据换 `LoginUser` 写入 Redis 会话。"

### ✅ 可以放心讲的部分（代码完整）

> "登录链路是：认证通过后从 token 里取用户名（`sub`），拿它查本地 `sys_user` 表：
> - **查不到 → 返回 401**，提示"用户未注册"（**不做自动建号**，避免越权）；
> - 查得到 → 构建 `LoginUser`，加载**角色**、**菜单权限**、**角色权限**，生成内部 JWT，重定向回前端。
>
> 内部会话是 **JWT + Redis** 双轨：JWT 本身不存 `exp`，过期靠 Redis 会话 TTL 控制（默认 60 分钟），剩余不足 20 分钟时**滑动续期**。
> 这样做的好处是**服务端可以主动踢人**（异地登录、管理员强制下线），纯 JWT 做不到。"

### 高频追问

**Q1. 为什么不用纯 JWT？**
> "纯 JWT 无状态，签发后无法撤销，想踢人只能等它自然过期。放 Redis 就有了服务端控制权。"

**Q2. 标准 OAuth2 授权码流程是什么？**（八股，必须能答）
> "① 前端带 `client_id`、`redirect_uri`、`scope`、`state` 跳授权端点；② 用户登录授权，认证中心带 `code` 回调；③ 后端用 `code` + `client_secret` 换 `access_token`（和 OIDC 的 `id_token`）；④ 校验 `id_token` 的**签名、`iss`、`aud`、`exp`、`nonce`**；⑤ 建立自己的会话。
> `state` 防 CSRF，`nonce` 防重放，两个都要服务端存下来回调时比对。"

**Q3. 你代码里 JWT 是怎么下发的？**（会被问，且**有安全问题**）
> "⚠️ 老实说**有两处待改进**：① JWT 通过**URL query 参数**重定向下发，会残留在浏览器历史和 Nginx 日志里；② 调试时用 `System.out.println` 打了完整 token。
> 正确做法是：重定向只带一个**一次性授权码**，前端用它调后端换 token；或者用 `HttpOnly + Secure` 的 Cookie 承载。"

> 💡 **主动承认安全问题，比被追问出来强十倍。**面试官问这句本来就是在测安全意识。

### 避坑提示

- 🚫 不要说"我做了 `id_token` 校验"——没有
- 🚫 不要说"OIDC 协议接入已完成"
- ✅ Q3 的两处安全问题主动交代，加分

**Q1. 你觉得这个项目有什么问题？**（必问，别答"没有"）

> "平台侧需要跨租户统计时，我们走的是**平台 schema 的汇总**，而不是遍历所有租户 schema——遍历的成本随租户数线性增长。"
